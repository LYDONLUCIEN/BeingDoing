## 二、本次迁移的 3 个特殊注意点

1. **配置必须按步骤 2 统一并自动预检**：新版生产启动强制检查密钥、`DEBUG=False`、`REFRESH_COOKIE_SECURE=True`，不满足直接拒绝启动；`NEXT_PUBLIC_SITE_URL` 还决定生产 robots/sitemap。不要再用会打印配置值的 `grep | sed` 预检。
2. **数据库迁移 4 个**：`023`（退款：payment_order_lines、payment_refunds、orders 加 amount_refunded）→ `024`（券多次核销：coupon_redemptions、coupons 加列+存量回填）→ `025`（users 加 user_type/admin_note）→ `026`（refunds 加 revoke_codes）。目标 head = `026_refund_revoke_codes`。
   ⚠️ OPERATIONS.md §4.4 写的 head 是 `025`，为文档滞后，以 `alembic heads` 实际输出 `026_refund_revoke_codes` 为准。
3. **依赖必须按锁文件安装**：后端用 `pip install -r src/backend/requirements.lock`（要求 Python 3.12）；前端 `npm ci --include=dev`（新增 rehype-sanitize）。不要用 `npm audit fix --force` 改版本。

站内公告功能生产已存在，**升级前直接在生产后台发布维护预告**：

  - 内容：维护时间窗口（如「10 月 X 日 22:00-23:00 系统升级，期间暂不可访问」）

升级完成、验收通过后，再发一条「升级完成」公告（或把预告公告停用）。

## 四、迁移执行步骤（生产服务器）

> 全程同一 SSH 会话执行；任何一步报错就停下排查，不继续。环境选择、Conda、`bd_load_env` 函数定义见 [OPERATIONS §2](../../../docs/OPERATIONS.md)，本文不重复。

### 步骤 1：环境确认与锁定目标

在做什么：确认工作区干净、记录当前版本用于回滚、锁定发布 SHA。

```bash
cd /home/gitclone/BeingDoing
export BD_OPS_ROOT="$(pwd -P)" BD_OPS_ENV=prod
export CONDA_BASE=/root/miniconda3 CONDA_ENV=base   # 按实际调整
source "$CONDA_BASE/etc/profile.d/conda.sh" && conda activate "$CONDA_ENV"
python -c 'import sys; assert sys.version_info[:2]==(3,12)'

git fetch origin
git status --short                                   # 应为空
export BD_OPS_PREVIOUS="$(git rev-parse HEAD)"       # 应是 838920cb...
export BD_OPS_TARGET=6df077d06419f7360d3dce8e5e6d78d4eb4b3ff5
git show --no-patch --oneline "$BD_OPS_TARGET"

# 只读配置检查器的版本：填包含该脚本的 dev 已验收完整 40 位 SHA
# 它不是第二个运行版本；BD_OPS_TARGET 仍固定为上面的 v1.8.3。
export BD_ENV_CHECK_REV='替换成包含check_env.py的dev已验收完整40位提交SHA'
git cat-file -e "${BD_ENV_CHECK_REV}^{commit}"
git show "${BD_ENV_CHECK_REV}:scripts/check_env.py" > /dev/null
```

验证：`git rev-parse v1.8.3^{commit}` 输出与 `BD_OPS_TARGET` 一致；最后一条 `git show` 能读到检查器。工具提交不要求是 v1.8.3 标签的一部分。

### 步骤 2：统一配置并自动预检（先 dev 后 prod，必做）

只做下列调整。两台服务器分别编辑自己的文件，**不要互拷整份 env，不要重新生成现有密钥，也不要把真实值贴到手册、聊天或 Git**。

#### 2.1 做什么

**两边的根 `.env`（基础层）：**

- 注释或删除活动的 `LLM_FLASH_MODEL=deepseek-v4-pro`；主要场景模型以后只看 admin「模型场景」配置。
- 将 `TEAM_ANALYSIS_EMAIL`、`NEXT_PUBLIC_SITE_URL`、三个 `ALIPAY_*` 的活动值放到对应覆盖层，避免基础层隐式串环境。
- 其他现有配置和密钥不打印、不入 Git、不互拷。签名、模型 API、SMTP/IMAP、OSS 等秘密必须由覆盖层按环境提供；不要让 dev/prod 从同一个基础值继承成相同秘密。
- 根 `.env` 是两台机器各自的私有文件，不是要求内容完全相同的文件。若测试侧暂时没有独立 SMTP/OSS/某个模型凭据，可在 dev 覆盖层显式留空并记录该外部能力不可用，不能复用生产秘密。

**dev 机的 `.env.dev`（覆盖层）核对为：**

```bash
APP_ENV=development
DEBUG=True
DEBUG_MODE=True
FRONTEND_URL=https://career.beyondego.me
NEXT_PUBLIC_SITE_URL=
TEAM_ANALYSIS_EMAIL=openlife.lab@outlook.com
ALIPAY_NOTIFY_URL=https://openlife.beyondego.me/api/v1/payment/notify/alipay
ALIPAY_RETURN_URL=https://openlife.beyondego.me/payment/result
ALIPAY_GATEWAY=https://openapi.alipay.com/gateway.do
```

这里是有意保留的共享支付例外：dev 也用正式支付宝和 openlife 回调/回跳，**不是沙箱**。生产域名不可用时，dev 的 notify/return 同样受影响；主动查单兜底不等于真实支付已验收。

**prod 机的 `.env.prod`（覆盖层）核对为：**

```bash
APP_ENV=production
DEBUG=False
DEBUG_MODE=False
REFRESH_COOKIE_SECURE=True
FRONTEND_URL=https://openlife.beyondego.me
NEXT_PUBLIC_SITE_URL=https://openlife.beyondego.me
TEAM_ANALYSIS_EMAIL=openlife.lab@outlook.com
ALIPAY_NOTIFY_URL=https://openlife.beyondego.me/api/v1/payment/notify/alipay
ALIPAY_RETURN_URL=https://openlife.beyondego.me/payment/result
ALIPAY_GATEWAY=https://openapi.alipay.com/gateway.do
```

生产现有 `SECRET_KEY` 必须保留且去空白至少 32 字符、不能是公开默认占位符；独立 `REFRESH_TOKEN_SECRET_KEY` 如配置也至少 32 字符。`REFRESH_COOKIE_SECURE=True` 只是新增必需项，不会自动开启 HTTPS，TLS 仍按原部署验收。

> Git 版本边界：新机制提交后，真实 `.env`/`.env.dev`/`.env.prod` 都只留本机，Git 只跟踪脱敏 `*.example`。但旧 `v1.8.3` 标签本身仍跟踪 `.env.dev`，所以本次切到该标签时，**不要在 `.env.dev` 写任何密码或密钥**；dev 秘密继续放已忽略的根 `.env`，prod 秘密放已忽略的根 `.env` / `.env.prod`。

#### 2.2 验证

dev 在已经包含检查器的代码根目录执行：

```bash
python scripts/check_env.py --env dev --base .env --overlay .env.dev
```

prod 在切换旧 `v1.8.3` 代码前，使用步骤 1 锁定的独立工具提交执行：

```bash
git show "${BD_ENV_CHECK_REV}:scripts/check_env.py" | \
  python - --env prod --base .env --overlay .env.prod
```

如果两份配置**本来就合法地位于同一受控目录**，可额外检查应隔离的签名/模型/邮件/OSS 秘密是否相同：

```bash
git show "${BD_ENV_CHECK_REV}:scripts/check_env.py" | \
  python - --env all --base .env --dev .env.dev --prod .env.prod
```

不要为了这项比较把生产秘密复制到 dev。没有同时持有两份配置时，分别执行 dev/prod 检查即可。若比较发现相同，先排查是否继承错文件或拿错配置；若真实两环境确实共用秘密，不要为赶发布直接轮换生产密钥，应另行评估登录失效和模型配置密文影响。

#### 2.3 理论结果

- 所有必需规则显示 `PASS`、退出码为 0 才继续；dev 的共享正式支付宝/openlife 依赖显示 `INFO` 是预期结果。
- 任一 `FAIL` 或退出码非 0：停止迁移，只修正对应配置后重跑；输出不会显示密码、密钥值或原始配置行。
- `PASS` 仅表示静态配置符合规则，不代表 DNS、nginx、数据库、真实支付、SMTP 或 LLM 已连通。
- prod 后续重新构建并启动后：后端不再被生产安全校验拒绝；robots 不再是全站 `Disallow: /`，sitemap 应包含一条生产首页，canonical 指向 `https://openlife.beyondego.me`。

### 步骤 3：开启维护模式

在做什么：公网切到维护页，阻止用户写入。

```bash
./scripts/maintenance.sh on --env prod --reason '版本升级 v1.8.3'
./scripts/maintenance.sh status --env prod
```

验证：用**无维护绕过 cookie** 的浏览器访问域名，确认看到维护页（脚本输出 ON 不代表 nginx 已拦截）。

### 步骤 4：停服 + 一致备份

在做什么：停全部写入后，同一时点备份 DB、`data/`、环境配置与依赖记录。

```bash
./start.sh stop
ss -ltnp '( sport = :8000 or sport = :3000 )'        # 应无本应用监听
```

然后按 [OPERATIONS §4.2](../../../docs/OPERATIONS.md) 的备份脚本执行（解析 DATABASE_URL → SQLite Backup API → 复制 data 与 .env → 生成 `BACKUP_COMPLETE`）。

验证：`test -f "$BD_OPS_BACKUP/BACKUP_COMPLETE"` 存在才继续。

### 步骤 5：切换代码 + 安装依赖

在做什么：切到 v1.8.3，按锁文件装后端依赖、按 lockfile 装前端依赖。

```bash
git switch --detach "$BD_OPS_TARGET"
test "$(git rev-parse HEAD)" = "$BD_OPS_TARGET"
python -m pip install -r src/backend/requirements.lock && python -m pip check
cd src/frontend && npm ci --include=dev && npm ls rehype-sanitize --depth=0 && cd "$BD_OPS_ROOT"
```

验证：`pip check` 无冲突；`npm ls` 显示 `rehype-sanitize@6.0.0`。报告渲染器 `dist/` 已随代码提交，无需重建。

### 步骤 6：配置自检 + 数据库迁移

在做什么：用新版代码校验配置指向原 DB，然后执行 4 个 Alembic 迁移。

```bash
bd_load_env
cd "$BD_OPS_ROOT/src/backend"
python -m alembic current      # 期望 022_abuse_detection
python -m alembic heads        # 期望 026_refund_revoke_codes（唯一 head）
python -m alembic upgrade head
python -m alembic current      # 期望 026_refund_revoke_codes
```

验证：current 从 `022` 变为 `026`；无报错。若 current 无版本/多 head/报 missing revision，**停止**，不要 `stamp head`。
另需先跑 OPERATIONS §4.3 的配置校验片段（确认新配置仍指向备份的那个 DB 文件）。

### 步骤 7：启动 + 本机验收

在做什么：以 prod 模式启动（start.sh 会重建前端），先在本机绕过公网验证。

```bash
cd "$BD_OPS_ROOT"
BD_SKIP_TMUX_ATTACH=1 ./start.sh start prod
tmux capture-pane -p -S -100 -t beingdoing:backend    # 看后端日志无启动报错
tmux capture-pane -p -S -100 -t beingdoing:frontend   # 等前端构建完成

curl --fail --max-time 10 http://127.0.0.1:8000/health        # {"status":"healthy"}
curl --fail --max-time 10 http://127.0.0.1:3000/ -o /dev/null
```

验证：health 返回 healthy、前端 200、后端日志无配置校验报错。

### 步骤 8：带维护绕过的业务验收

在做什么：管理员经维护绕过访问，按本次改动逐项点验（prod 不制造真实扣款/退款）。

- [ ] 登录/刷新、普通账号权限正常；历史报告可打开、PDF 可下载
- [ ] 后台 `/admin/users`：用户类型标签、备注可编辑
- [ ] 后台支付管理：退款能力查询、订单明细 xlsx 导出可下载（验证 openpyxl）
- [ ] 后台券管理：多次核销券创建/列表正常
- [ ] 后台 `/admin/site-notices`：公告 CRUD 正常
- [ ] 手机宽度（浏览器 DevTools 设备模拟）：聊天抽屉、首页阶段卡纵向排列正常
- [ ] 四阶段与 v4 对话 SSE 正常
- [ ] 公网 `/robots.txt` 不再是单独的全站 `Disallow: /`；`/sitemap.xml` 包含一条 `https://openlife.beyondego.me` 首页；首页 canonical 指向生产域名

### 步骤 9：关闭维护 + 发布完成通知

```bash

git rev-parse HEAD     # 记录为发布版本
```

验证：无绕过 cookie 的浏览器访问公网恢复正常。然后在后台发布「升级完成」公告（或停用维护预告）。保留本轮备份目录与验收记录。

## 五、回滚（仅当验收失败且无法现场修复）

```bash
./scripts/maintenance.sh on --env prod --reason '版本回滚'
./start.sh stop
git switch --detach "$BD_OPS_PREVIOUS"        # 回到 838920cb
# 恢复备份：database.sqlite 还原到原 DB 路径，data/ 整目录还原
python -m pip install -r src/backend/requirements.txt   # 旧版本无 lock，按旧清单
cd src/frontend && npm ci --include=dev && cd "$BD_OPS_ROOT"
BD_SKIP_TMUX_ATTACH=1 ./start.sh start prod
curl --fail http://127.0.0.1:8000/health
./scripts/maintenance.sh off --env prod
```

要点：代码回滚**必须同时还原数据库备份**（023-026 已改表结构，旧代码不认识新表）；回滚后同样走步骤 8 的核心项验收。
