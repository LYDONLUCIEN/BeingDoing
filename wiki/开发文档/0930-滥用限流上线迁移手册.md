# 滥用检测系统上线 · 升级迁移手册

> 适用版本：2026-09-30 滥用检测与限流系统（abuse detection）
> 目标环境：生产服务器（openlife.beyondego.me）
> 预计停机时间：**0 分钟**（迁移为加表，不影响在线服务；重启后端秒级）
> 风险等级：低（新增两张表 + 门控逻辑，fail-open 设计——即使迁移漏跑，聊天主流程也不会断，只是限流不生效）

---

## 0. 变更内容速览

| 类别 | 内容 |
|---|---|
| 数据库 | 新增迁移 `022_abuse_detection`：建 `abuse_events`（事件流水）、`abuse_states`（警告/冻结状态机）两张表 |
| 后端 | 滥用检测门控（挂载全部聊天写端点）、admin `/admin/abuse/*` 四个端点、startup 加载冻结名单 |
| 前端 | admin 新增「滥用监控」页；chat 页新增 429 警告条 / 403 冻结弹层 |
| 运行时配置 | 新增 `data/abuse_config.json`（阈值配置，admin 页即改即生效，**无需重启**） |

**部署顺序铁律：先迁移数据库，再重启后端。**（反过来的后果也只是限流不生效并刷错误日志，不会宕机，但别这么做。）

## 1. 升级步骤（生产）

### 1.1 登录生产服务器，进入项目目录

```bash
ssh <生产机>
cd /home/gitclone/BeingDoing        # 以实际部署路径为准
```

### 1.2 拉取代码

```bash
git fetch --all
git checkout <发布分支或tag>         # 按发布流程
git pull
```

### 1.3 备份数据库（SQLite，秒级，强烈建议）

```bash
cd src/backend
cp app.db app.db.bak-$(date +%Y%m%d-%H%M%S)
```

### 1.4 执行数据库迁移

```bash
# 生产机 conda 为 base 环境（/root/miniconda3），alembic 已装
cd /home/gitclone/BeingDoing/src/backend
alembic current                     # 确认当前在 021_user_avatar
alembic upgrade head                # 升级到 022_abuse_detection
```

预期输出：

```
INFO  [alembic.runtime.migration] Running upgrade 021_user_avatar -> 022_abuse_detection, abuse detection
```

> ⚠️ 若 `alembic` 命令找不到：`source /root/miniconda3/etc/profile.d/conda.sh && conda activate base` 后重试。

### 1.5 重启服务（加载新代码 + 前端重新构建）

```bash
cd /home/gitclone/BeingDoing
./start.sh prod                     # 加载 .env → .env.prod，clean build + start
```

> 只重启后端用 `./start.sh restart backend`（前端无构建缓存问题时够用；
> 但本次前端有改动，**首次部署请用 `./start.sh prod` 全量**）。

### 1.6 验证（按顺序执行，全部通过才算上线成功）

```bash
# ① 后端健康
curl -s http://127.0.0.1:8000/health
# 预期: {"status":"healthy"}

# ② 迁移到位（应输出 022_abuse_detection）
cd src/backend && alembic current

# ③ 两张新表存在
sqlite3 app.db ".tables" | tr ' ' '\n' | grep abuse
# 预期: abuse_events  abuse_states

# ④ 新 admin 端点已注册（无 token 应返回 401，证明路由存在且鉴权生效）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/api/v1/admin/abuse/config
# 预期: 401
```

然后浏览器人工验证：

1. 超管登录 → admin 后台 → 左侧导航出现「**滥用监控**」（用户管理下方）→ 打开能看到阈值配置卡片
2. 正常用户账号 → chat 页发一条消息 → 正常回复（确认门控没误伤正常流量）
3. nginx 访问日志抽查 `/api/v1/simple-chat/message/stream` 无 5xx 异常增多

## 2. 上线后配置（可选，默认值已合理）

admin → 滥用监控 → 阈值配置（即改即生效，无需重启）：

| 配置项 | 默认值 | 含义 |
|---|---|---|
| enabled | true | 总开关 |
| msg_per_minute | 10 | 单用户 1 分钟消息上限（超过触发） |
| msg_per_hour | 360 | 单用户 1 小时上限 |
| msg_per_day | 1000 | 单用户 1 天上限 |
| token_lifetime | 5000000 | 单用户累计 token 上限 |
| thread_delete_per_phase | 3 | 同一阶段累计删除对话上限 |

> 压测期间务必临时把 `enabled` 关掉或调高阈值，否则压测账号会被限流系统正常冻结。

## 3. 回滚方案

### 3.1 代码+迁移完整回滚

```bash
cd /home/gitclone/BeingDoing
./start.sh stop

cd src/backend
alembic downgrade 021_user_avatar   # 删掉 abuse_events / abuse_states 两张表

cd /home/gitclone/BeingDoing
git checkout <上一个稳定tag>
./start.sh prod
```

### 3.2 只关闭功能、不回滚代码（推荐的首选止血）

admin → 滥用监控 → 把 `enabled` 置为 false 即可（即改即生效）。

或用命令行直接改配置：

```bash
cd /home/gitclone/BeingDoing
echo '{"enabled": false}' > data/abuse_config.json
# mtime 缓存自动失效，下次请求即生效，无需重启
```

### 3.3 紧急解冻某用户（不经过 admin 页面时）

```bash
cd /home/gitclone/BeingDoing/src/backend
sqlite3 app.db "DELETE FROM abuse_states WHERE user_id='<user_id>';"
# 内存冻结名单重启后失效，重启后端：
cd /home/gitclone/BeingDoing && ./start.sh restart backend
# 被 revoke 的激活码需到 admin 激活码管理页手动改回 active
```

## 4. 常见问题

**Q：忘了跑迁移就重启了会怎样？**
A：不会宕机。abuse 检查是 fail-open——查不到表时记错误日志并放行，聊天正常，但限流完全不生效，admin 滥用监控页会报错。补跑 `alembic upgrade head` 即可，无需再重启（下次请求自动生效；但内存冻结名单是 startup 加载的，补迁移后建议 `./start.sh restart backend` 一次）。

**Q：存量用户的历史 token 会被追溯吗？**
A：会。`token_lifetime` 统计的是 `llm_usage_logs` 全量累计，上线即有历史基数。但 500 万 token 的阈值远超正常用户（均值约 100 万），且首次触发只警告不冻结，不会误伤。

**Q：被冻结的用户看到什么？**
A：chat 页弹「账号存在异常操作，聊天功能已冻结」弹层 + 联系邮箱 openlife.lab@outlook.com，输入框禁用；只读页面（历史、报告）不受影响。同时用户会收到站内信和邮件，超管收到 `abuse_frozen_admin` 站内信。

**Q：解冻操作在哪？**
A：admin → 滥用监控 → 已冻结 tab → 「解冻恢复」（自动把被 revoke 的激活码恢复为 active，用户即刻可聊）。
