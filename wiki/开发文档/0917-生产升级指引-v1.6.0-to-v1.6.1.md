## 2. 升级步骤（停服窗口内，约 3 分钟）

```bash
cd /path/to/BeingDoing

# 2.1 拉代码
git fetch --tags
git pull --ff-only              # 或 git checkout v1.6.1
git log -1 --oneline            # 确认 HEAD 为 v1.6.1（e78062b）
git status --short              # 确认无本地未提交改动被带入

# 2.2 停服
./start.sh stop

# 2.3 备份数据库（SQLite 文件级备份，停服后冷备最稳）
cp src/backend/app.db src/backend/app.db.bak-before-021
ls -lh src/backend/app.db.bak-before-021   # 确认大小与 app.db 一致

# 2.4 装新依赖（Pillow，生产 conda base 环境）
source /root/miniconda3/etc/profile.d/conda.sh && conda activate base
pip install "Pillow>=10.0.0"
python -c "import PIL; print(PIL.__version__)"   # 预期 ≥10.0.0

# 2.5 执行数据库迁移
cd src/backend
alembic upgrade head            # 019 → 020 → 021，秒级完成
alembic current                 # 预期：021_user_avatar (head)
cd ../..

# 2.6 启动（⚠️ 必须显式 prod，裸跑 ./start.sh 会走 dev 的 conda 默认值）
./start.sh prod
```

> 说明：020 迁移内含一条 `UPDATE coupons SET expires_at = 迁移时刻+90天` 的存量追溯 SQL，券表量级下为毫秒级，不影响停服窗口。

## 4. 回滚方案

数据迁移为纯加列（+一条 UPDATE），**回滚首选恢复备份**：

```bash
cd /path/to/BeingDoing
./start.sh stop
cp src/backend/app.db.bak-before-021 src/backend/app.db   # 恢复 DB
git checkout v1.6.0                                        # 回退代码
./start.sh prod
```

备选（不丢升级后新数据时）：`alembic downgrade 019` 只掉新增列与索引，020 的 UPDATE 不回溯（券的 expires_at 随列一起删除），亦可接受；但注意升级后若已有用户上传过头像，`avatar_url` 列会被 drop，头像记录丢失。

## 附录 A：OSS 配置缺失时补齐

从头像功能口径：dev/prod 共用同一 bucket（`soulhappy-hermes-agent`）与现有 RAM key，不分桶。把开发机 `.env` 里的 5 项 OSS 配置复制到生产 `/etc/beingdoing.env`（systemd 场景）或 `.env.prod`（start.sh 场景）：

```bash
# 在生产机上查看开发机 .env 对应项后写入（值从开发机 .env 抄）：
OSS_ACCESS_KEY_ID=...
OSS_ACCESS_KEY_SECRET=...
OSS_ENDPOINT=oss-cn-shanghai.aliyuncs.com
OSS_BUCKET_NAME=soulhappy-hermes-agent
OSS_PUBLIC_BASE_URL=
```

补完后 `./start.sh restart backend` 即可生效，无需重新迁移。
