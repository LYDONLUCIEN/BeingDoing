# 结论卡机制全景（当前 main，2026-09-27 梳理）

> 适用范围：simple-chat 四阶段（values / strengths / interests / purpose）。rumination 阶段**不走结论卡**（v4 为用户手填 hypothesis + 后台平衡点判定，见 `rumination_v4_prompt.py`）。
> 关键文件：后端 `src/backend/app/api/v1/simple_chat_routes.py`（机制主战场）、`core/dimension_completion_checker.py`、`domain/conclusion_card_payload.py`、`domain/dimension_completion.py`、`api/v1/simple_chat/stream_utils.py`；前端 `app/(main)/explore/chat/[phase]/page.tsx`、`components/explore/DimensionConclusionCard.tsx`、`ConclusionRequestButton.tsx`、`TrialLimitModal.tsx`、`ContinueConfirmModal.tsx`。

## 状态机

```
none ──模型输出 STATE_JSON(pending_ready)──▶ pending ──用户点「确认没有问题」──▶ confirmed（终态，thread_completed=true）
  ▲                ▲                          │
  │                │                          ├─用户点「我想再聊聊」→ rejected
  │                └─rejected 满 3 轮 retrigger─┤
  └────手动按钮（常驻，点击即判定）─────────────┘（rejected 后再点头 → 模型重新出卡回 pending）
```

- 状态仅存对话文件 metadata（`conclusion_state / conclusion_draft / conclusion_final / conclusion_feedback / conclusion_shown_at_turn / thread_completed`），**不写消息文件**。
- 读写统一走 `_read_conclusion_meta` / `_build_conclusion_meta_update`（routes L622-695；pending 才留 draft，rejected 才留 feedback，confirmed 置 `thread_completed=true`）。

## 一、提示词侧的两个注入点（每轮 system prompt）

1. **[输出协议] 块**（`_build_system_prompt` routes L4183-4247）：四阶段在 base_prompt 后追加，声明 `[STATE_JSON]{"state":"continue|pending_ready","draft":{...}}[/STATE_JSON]` + 按阶段的 draft 扩展字段说明（`build_state_json_draft_extension_protocol`）。自然出卡**不设最小轮数**（2026-09-02 起撤销 ≤10 轮压制）。
2. **[结论卡状态·内部参考]**（`build_conclusion_state_injection`，payload L115-185；调用点 event_stream L6374-6401）：拼在 system **最末尾**（prefix cache 考虑）。内容 = 三态转换规则 + `当前状态：none|pending|rejected|confirmed` + 补充信息（pending→草案摘要+关键词；rejected→上版摘要+清洗后拒绝理由+「距上次拒绝已补充 N 轮」）。rumination 与 thread_completed 不注入。

## 二、三条出卡路径（后端视角）

| 路径 | 触发 | 生成方式 | 落库 |
|---|---|---|---|
| **A. 自然出卡** | 模型当轮输出 `STATE_JSON(pending_ready)`（routes L6887-6984） | sanitize → purpose 用 confirmed_rows 覆盖 → **再走一次生成器 refine**：`check_dimension_complete(prior_conclusion=draft, skip_completion_check=True)`（失败回退原 draft） | pending |
| **B. retrigger** | rejected 后满 3 个用户轮次（`CONCLUSION_REJECT_NUDGE_USER_TURNS=3`）且本轮未自然出卡（L6988-7060） | `check_dimension_complete(skip_completion_check=True)` | pending |
| **C. 手动兜底按钮** | `POST /simple-chat/conclusion/request`（2026-09-27 起点击即判定） | 判定通过→同 B；不通过→引导话术 | pending / 不出卡 |

**confirmed 入口**：卡片「确认没有问题」→ `POST /simple-chat/thread/complete`（另有 pending-judge 判 confirmed 的流内分支 L6146-6302）。
**rejected 入口**：卡片「我想再聊聊」→ `POST /simple-chat/thread/reopen`（L4738-4855：置 rejected、feedback=「用户选择再聊聊…」、清 draft、记 `conclusion_reject_baseline_user_count`）；或 pending-judge 判 rejected/continue。

## 三、隐藏块的流式处理（用户看不到协议）

- `stream_utils.py:strip_hidden_blocks_for_stream / build_stream_hidden_block_filter`：逐 chunk 过滤 `[STATE_JSON]` 块（去闭合块、截未闭合块、暂存 marker 前缀防闪现），过滤后才推 `chunk` SSE。
- 流末 `_split_visible_reply_and_state` 解析出 state_obj；pending_ready 时推 `conclusion_loading:true` → 写 metadata → 推 `dimension_conclusion` SSE（前端当轮弹卡，无需刷新）。

## 四、前端小卡片（pending 卡）

- **到达方式**：纯 SSE 推送（非轮询）。`conclusion_loading` → 显示「正在生成结论卡片」提示条；`dimension_conclusion` → 插入卡片消息，历史卡全部 `conclusionLocked` 冻结。刷新兜底：`GET /simple-chat/history` 带 metadata，前端 `mergePendingDraftIntoMessagesFromMeta` 补卡。
- **pending 期间锁输入**：`pendingConclusionChoiceBlocksChat` —— 末条卡未表态时输入框只读，用户必须二选一：
  - 「确认没有问题」→ `thread/complete`：落 confirmed + `thread_completed=true`、写 note、写锚点、写 `dimension_conclusions.json` 快照、`save_prior_context_for_report` 存给下一阶段、触发后台锚点提炼；前端庆祝粒子 + PhaseCompleteWarmModal。
  - 「我想再聊聊」→ `thread/reopen`：置 rejected，本地折叠旧卡，输入恢复。
- **卡片组件** `DimensionConclusionCard.tsx`：summary（markdown）+ keywords 标签（strengths 带 a/b/c 禀赋角标、values 带理解、interests 带理由、purpose 带使命三段+经历-价值观表）；已确认后显示「已确认」+「完善答案」；stepLocked 后纯浏览。
- **「完成并继续」分离**：确认卡 ≠ 进下一阶段。顶栏按钮需 `canContinue`（线程 completed/stepLocked），点击后未锁定先弹 `ContinueConfirmModal`（告知进入下一阶段后本阶段对话与结论卡锁定不可改），确认才导航 `/explore/transition`。

## 五、retrigger（拒绝后自动重出卡）

每轮重读 meta 算 `turns_since_reject = user_count - baseline`；≥3 且无 pending、非 rumination、未 completed → 本轮流末若模型没自然出卡，后端直接 `check_dimension_complete(skip_completion_check=True)` 生成新 draft 置 pending 并推卡（note 标 `source:"retrigger_after_rejected"`；触发后 baseline 更新为当前轮数防重复）。

## 六、手动兜底按钮（2026-09-27 改版：常驻 + 点击即判定）

- **显示条件**（前端 `showConclusionRequestButton`）：非 completed && 报告未解锁 && **无待表态卡** && 末卡未确认 && 至少有过 1 条用户消息。**常驻，不再设 11 轮门槛**（`CONCLUSION_MIN_USER_TURNS` 已删除）。渲染在输入框上方；首次冒泡动画 + 闲置 10s/60s 抖动提醒（各一次，封顶 2 次）。文案：zh「生成阶段小结」。
- **点击后后端流程**（`request_conclusion_card` 重写）：
  1. 预检不变（trial 阶段锁 402 / rumination 400 / thread_completed 400 / pending/confirmed **幂等**返回）；
  2. **裁判判定**：`judge_dimension_completion`（判定门拆出的独立函数，返回 complete+reason；超时 30s `CONCLUSION_JUDGE_TIMEOUT_SECONDS`）；
  3. **判定通过** → `check_dimension_complete(skip_completion_check=True)` 生成草案置 pending（原逻辑不变，生成超时 60s）；
  4. **判定不通过** → 不生成卡片，`_build_conclusion_not_ready_guidance` 把判定理由编成引导话术（固定模板+reason；**试用码附升级引导**，避免「继续聊」被 10 轮 402 拦截成死路），作为 assistant 消息插入对话流（**数据结构/数据库均不变**，溯源走 note `conclusion_request_not_ready` + llm_turns 的 conclusion 场景记录）；
  5. **判定失败/超时** → 503「判定失败，请稍后点击重试」，不静默、不擅自出卡。
- **前端处理**：`not_ready=true` 时把 `guidance` 作为一条 assistant 消息本地插入对话流（后端已落盘，刷新一致）；点击期间冻结输入框与发送。
- **模型归属**：判定与生成统一挂 **conclusion 场景**（2026-09-27 起从 chat 拆出，admin「AI 模型分流」页可独立调 flash/pro + 思维链开关）；path A refine 与 retrigger 同步挂 conclusion 场景。

## 七、试用码（trial）联动

- `TRIAL_VALUES_USER_MESSAGE_LIMIT = 10`（`utils/trial_codes.py`，统计 report 全部 values 线程非 internal 用户消息）。
- values 内 ≥10 轮 → 402 `trial_limit_reached`；非 values 写操作 → 402 `trial_phase_locked`（detail 均带 `has_upgrade_codes` 供前端引导分级）。
- 与出卡关系：自然出卡不受轮数压制；但试用用户确认卡后点「完成并继续」→ 下一阶段 init 被 402 拦截 → 前端弹 `TrialLimitModal`（无码主按钮=购买；有码主按钮=「使用已有激活码升级」）。

## 八、结论生成器（check_dimension_complete）

`core/dimension_completion_checker.py`：
- **完成判定门**：`skip_gate = prior_conclusion 存在 or skip_completion_check`。不跳过时先跑 `judge_dimension_completion`（2026-09-27 拆出的独立判定函数，返回 complete+reason，供手动按钮「点击即判定」复用），`complete=false` 返回 None。自然出卡 refine 与 retrigger 全部 skip；**手动按钮端点改为显式先判定**。
- **生成**：专用 system（禁元叙述/禁杜撰）+ basic_info（截1200字）+ prior_context（截2200字）+ 近60条/12000字对话 + 结论规则 + 按阶段 JSON schema（`build_conclusion_json_schema_instructions`）；有 prior_conclusion 时注入「上一轮结论，综合更新」段。
- **解析**：去 ```json 包裹 → keywords 校验（strengths 截前5）→ `merge_conclusion_payload` 合并/对齐扩展字段（summary/keywords/ai_summary/final_answer + keyword_notes/strength_markers/interest_reasons/mission_* 等）。
- 结论相关 LLM 调用 max_tokens 统一 8192、超时 60s（历史截断/超时事故根因，见代码注释 L266-276）。

## 九、阶段间衔接（prior_context）

- **写**：确认时 `save_prior_context_for_report(report_id, next_phase, "【X阶段结果】summary+关键词")` + `merge_dimension_conclusion_record` 写四维快照 `dimension_conclusions.json`。
- **读**：下一阶段 `load_prior_context_from_activation` → 优先从 `dimension_conclusions.json` 按前置阶段拼块（回退旧 `prior_context_{phase}.txt`）→ 进 system prompt 的 `prior_block`，同时传给结论生成器。
- purpose 阶段另注入 `values_info`（values 关键词+理解）与 `purpose_progress` 进度块。

## 十、注意：死代码 / 易踩坑

1. `simple_chat/prompt_builder.py:build_system_prompt`（带 `conclusion_state_injection` 参数）**不是运行时路径**——仅 admin 提示词预览用；运行时拼接在 routes 本地 `_build_system_prompt`（L4183）+ event_stream 末尾注入（L6390）。
2. `templates/pending_conclusion_reply.yaml` = **孤儿模板**（无任何引用），旧方案遗留，已被统一状态注入取代；`build_pending_main_dialogue_system_addon` 同为死代码。
3. `answer_card_summary.yaml` 只服务 full/LangGraph 架构的答题卡（`core/agent/question_flow.py`），与 simple-chat 结论卡无关。
4. pending 期间曾有「用户发消息 → 独立 LLM 判定 confirmed/rejected/continue」的 pending-judge 路径（L1141-1364），现为保留路径（前端 pending 锁输入后用户基本发不出消息）。
