## 1. 关键变化清单（部署前必读）

### 1.1 数据库 Migration（4 个，链路完整）

```
003_add_email_verified (v1.4.0 head)
    ↓
004_notification        新增 notification_tasks / notification_recipients（邮件群发）
    ↓
005_fix_timestamps_tz   历史 naive 时间 → tz-aware（不可逆，SQLite 专属）
    ↓
006_email_bounces       新增 email_bounces（退信黑名单）
    ↓
007_site_notices        新增 site_notices（站内公告 / 维护 banner）
```

**链路校验**：`001 → 002 → 003 → 004 → 005 → 006 → 007`，单 head，无分叉（`002_enhance_likes` 重复文件已归档到 `_archive_duplicate/`）。

**⚠️ 005 不可逆**：`downgrade()` 是 `pass`，回滚不会去掉 `+00:00` 后缀。**升级前必须备份 app.db。**

### 1.2 配置变化（.env.prod）

新增 12 个变量，分 3 组：

#### A. 退信扫描（IMAP）—— 复用 SMTP 账号
```bash
BOUNCE_IMAP_HOST=imap.163.com        # 在 .env（base）配置，.env.prod 不放
BOUNCE_IMAP_PORT=993
BOUNCE_IMAP_USER=                    # 不填回退 SMTP_USER
BOUNCE_IMAP_PASS=                    # 不填回退 SMTP_PASS
BOUNCE_SCAN_CRON="0 3 * * *"         # 每日 03:00 扫一次
BOUNCE_SCAN_LOOKBACK_HOURS=48
BOUNCE_SCAN_SOFT_THRESHOLD=3
```

#### B. 维护模式 —— nginx 静态页硬拦截
```bash
# ⚠️ prod 机 1Panel 版本与 dev 不同，容器挂载是 /opt/1panel/www → /www（没有 apps/openresty/openresty 中间层）
# 容器名：1Panel-openresty-UpQ6（prod 机，与 dev 机的 1Panel-openresty-hjWm 不同）
MAINTENANCE_FLAG_PATH=/opt/1panel/www/sites/xunlu/maintenance.flag
MAINTENANCE_PAGE_DIR=/opt/1panel/www/sites/xunlu/maintenance
MAINTENANCE_TEMPLATE_PATH=/home/gitclone/BeingDoing/src/frontend/maintenance.html
NGINX_RELOAD_CMD="docker exec 1Panel-openresty-UpQ6 nginx -s reload"
BYPASS_COOKIE_NAME=bypass_maintenance
```

> **留空兜底**：如不显式设 `NGINX_RELOAD_CMD`，`maintenance.sh` 会自动 `docker ps` 找 `1Panel-openresty-*` 容器并组装命令（详见脚本）。

#### C. 前端 API 显式指向
```bash
NEXT_PUBLIC_API_URL=https://xunlu.soulhappylab.com   # 旧版为空，新版必须显式
```

**⚠️ dev/prod 路径与容器名都不一样**（已修正进仓库 `.env.prod`，此提醒仅供排查）：
- dev 机容器挂载：`/opt/1panel/apps/openresty/openresty/www → /www`（路径含中间层）
- prod 机容器挂载：`/opt/1panel/www → /www`（**无中间层**，1Panel 版本不同）
- dev 容器名：`1Panel-openresty-hjWm`；prod 容器名：`1Panel-openresty-UpQ6`
- 站点目录：dev 是 `zhiyinapp`，prod 是 `xunlu`

> **自动 env 选择**：前端 `setMaintenanceMode()` 会按域名自动选 env（`career.soulhappylab.com/localhost/IP` → dev；`xunlu.soulhappylab.com` → prod），无需手动指定。

### 1.3 后端启动行为变化（main.py）

启动时会自动执行（fire-and-forget，不阻断启动）：
1. **打印当前 DB alembic revision** → 排查代码/DB 是否对齐
2. **恢复中断的群发邮件任务** → status=running 标记为 interrupted
3. **启动 APScheduler 退信定时任务** → 日志见 `bounce scheduler started, cron='0 3 * * *'`
4. **CORS 新增** `https://xunlu.soulhappylab.com`、`http://xunlu.soulhappylab.com`

新增路由模块：
- `/api/v1/admin/notifications` — 邮件群发任务
- `/api/v1/admin/bounces` — 退信黑名单管理
- `/api/v1/site-notices` + `/api/v1/admin/site-notices` — 站内公告
- `/api/v1/admin/maintenance` — 维护模式切换（admin 触发）

- **Issue #50**：admin 页面按钮触发维护模式后 nginx 拦截不生效 → **已在本次 v1.5 修复**（根因：前端硬编码 `env=prod` + `.env.prod` 的 `NGINX_RELOAD_CMD` 错误）。详见 issue #50 / #51。
- **Issue #41 / #19 / #18 / #23**：Rumination 流程相关已知问题，不影响本次部署。

## 3. nginx 一次性配置（维护模式，必做一次）

**完整配置见** [`0705-nginx-prod.md`](./0705-nginx-prod.md)，这里只列操作步骤。

xunlu 站点的反代 location 走 `proxy/*.conf` include，**3 个文件都要改**：

| 文件 | 1Panel 路径 | 改动 |
|------|------------|------|
| 主配置 | 网站 → xunlu → 配置 | 加维护检测块（set/if/error_page/@maintenance） |
| `/` 反代 | 网站 → xunlu → 反向代理 → `/` 的 conf | location 第一行加 `if ($maintenance_on = 1) { return 503; }` |
| `/api/` 反代 | 网站 → xunlu → 反向代理 → `/api/` 的 conf | 同上 |

**主配置新增片段**（粘贴到 `error_log` 之后、location 之前）：

```nginx
set $maintenance_on 0;
if (-f /www/sites/xunlu/maintenance.flag) {
    set $maintenance_on 1;
}
if ($http_cookie ~* "bypass_maintenance=1") {
    set $maintenance_on 0;
}
error_page 503 @maintenance;
location @maintenance {
    root /www/sites/xunlu/maintenance;
    try_files /maintenance.html =503;
    add_header Cache-Control "no-store, no-cache, must-revalidate" always;
}
```

创建维护页目录（宿主机执行）：

```bash
mkdir -p /opt/1panel/apps/openresty/openresty/www/sites/xunlu/maintenance
chmod 755 /opt/1panel/apps/openresty/openresty/www/sites/xunlu/maintenance
```

**⚠️ Issue #50 提醒**：当前生产 nginx 配置可能存在「嵌套 if」错误（CLI 凑巧能工作，admin 按钮不工作）。应用本文档/`0705-nginx-prod.md` 的正确配置后，重新测试 admin 路径。

## 4. 部署执行（推荐用 deploy.sh，5 分钟）

### 4.1 推荐：一键部署脚本

```bash
cd /home/gitclone/BeingDoing

# dry-run 预演（强烈建议先跑一遍）
./deploy.sh --dry-run

# 实际部署（脚本会自动备份 DB → 不自动 pull，因步骤 2.2 已 pull → 停服务 → alembic upgrade → 启动 → 冒烟）
./deploy.sh --skip-pull
```

`deploy.sh` 的 6 步流程：
1. 备份 `app.db`
2. `git pull`（已用 `--skip-pull` 跳过）
3. `./start.sh stop`
4. **`alembic upgrade head`**（一次升到 007）
5. `./start.sh start prod`
6. 冒烟检测（openapi.json + bounces 路由）

部署结束会列出可选的一次性迁移脚本（默认跳过，按需选择）。

### 4.2 手动部署（不想用脚本）

```bash
cd /home/gitclone/BeingDoing

# 1. 停服务
./start.sh stop

# 2. 备份 DB
cp src/backend/app.db "src/backend/app.db.bak.$(date +%Y%m%d_%H%M%S)"

# 3. 加载环境变量（alembic env.py 读 settings）
unset DEBUG DEBUG_MODE LLM_PROVIDER LLM_BASE_URL LLM_MODEL \
      OPENAI_API_KEY DEEPSEEK_API_KEY GLM_API_KEY KIMI_API_KEY CLAUDE_API_KEY \
      NEXT_PUBLIC_API_URL FRONTEND_MODE FRONTEND_URL
set -a
[ -f ".env" ] && source ".env"
[ -f ".env.prod" ] && source ".env.prod"
set +a

# 4. 升级数据库
source /mnt/vdb1/miniconda3/etc/profile.d/conda.sh
conda activate py312
cd src/backend
alembic current           # 升级前：应为 003_add_email_verified
alembic upgrade head      # 升级到 007_site_notices
alembic current           # 验证：应为 007_site_notices

# 5. 验证新表存在
sqlite3 ./app.db ".schema email_bounces" | head -5
sqlite3 ./app.db ".schema site_notices" | head -5
sqlite3 ./app.db ".schema notification_tasks" | head -5

# 6. 启动
cd /home/gitclone/BeingDoing
./start.sh start prod
```

## 8. 排错速查

| 现象 | 排查 |
|------|------|
| 后端启动报 `apscheduler` 找不到 | 步骤 2.3 没执行，`pip install -r requirements.txt` |
| 启动日志没有 `bounce scheduler started` | IMAP 配置缺失或异常，查后端日志（不阻断启动，只 warn） |
| `alembic upgrade` 失败 | 检查 `alembic heads` 是否单 head；DB 已备份，修复后重跑 `alembic upgrade head` |
| `email_bounces` 表未创建 | `sqlite3 src/backend/app.db ".schema email_bounces"` 验证；`alembic current` 确认到 006/007 |
| 前端 `Failed to find Server Action` | 旧浏览器标签页缓存，硬刷新或关旧标签；确认 `.env` 的 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 是 base64 输出不是命令文本 |
| 维护模式开了但 nginx 不拦截 | 确认 `if ($maintenance_on = 1) { return 503; }` 在 location 内第一行（proxy_pass 之前）；用 curl 不用浏览器验证；优先用 CLI 不要用 admin 按钮（Issue #50） |
| `NEXT_PUBLIC_API_URL` 不生效 | 生产 build 必须在 build 时注入，重新 `npm run build` |
| 邮件群发 401 | 退信扫描把发件邮箱自己拉黑了？查 `/admin/bounces` |
