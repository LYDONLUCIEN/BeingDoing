# 订单系统与退款设计（2026-10-05）

> 来源：grill-me 设计拷问（3 轮，10 项决策全部锁定）。
> 需求参照：[订单系统要求.md](./订单系统要求.md)
> 关联 ADR：ADR-0005（渠道抽象）、ADR-0008（套餐商品化）、ADR-0014（套餐码退款规则）。

## 一、已锁定决策

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 部分退定价 | 套餐按「码分摊实付」折算建议上限（券按比例分摊、尾差归最后一码），admin 只能下调不能上调；咨询部分退无折算依据，admin 手输（上限=剩余可退，必填金额理由） |
| 2 | 流程统一 | 全退/部分退统一走 `payment_refunds` 退款申请单，一套状态机；现有 admin 直接退款接口收掉（转代录+审批） |
| 3 | 发票税务 | 本次不开发票模块；落准口径（每行分摊实付落库），退款单预留税相关字段 |
| 4 | 申请入口 | 用户「我的订单」页申请退款（选类型/码数/理由）→ admin 站内信+邮件双通道通知 → admin 审批页批/驳/改金额 |
| 5 | 订单状态 | 订单状态新增 `partially_refunded`；累计退款 = 实付时才置 `refunded` |
| 6 | 优惠券 | 部分退不退券；全退时券未过期则返还（保持现行为 used→unused） |
| 7 | 商品矩阵 | 套餐：全退（码全未动）/ 部分退（按未用码数折算，退几码作废几码）；咨询：全退+部分退（仅未预约）；延期：不可退；旧激活码：仅全退且未 claim；0 元单：同流程跳过渠道调用 |
| 8 | 申请治理 | 待审批可撤回；驳回必填理由（用户可见）；驳回后可重提不限次；同一订单同时只允许一个待审批申请 |
| 9 | 咨询边界 | 已预约/已完成的咨询不可退，走线下协商 |
| 10 | admin 代录 | 支持：线下谈好的退款由 admin 代录申请（originated=admin + 代录人留痕），保证审计链完整 |

## 二、数据库

### 2.1 `payment_orders`（改）

新增列：

| 列 | 类型 | 说明 |
|---|---|---|
| `amount_refunded` | INTEGER NOT NULL DEFAULT 0 | 累计**成功**退款（分），恒 ≤ `amount_paid` |

状态取值新增 `partially_refunded`（0 < amount_refunded < amount_paid 时表达）。

不变式：`amount_refunded == amount_paid ⇔ status == refunded`（0 元单除外：退款单成功作废码即可，渠道无调用）。

### 2.2 `payment_order_lines`（新：订单明细行 / 优惠分摊口径）

> 要求.md 第二节「实付分摊到行」的落地。**下单交付（granted）时生成并落库分摊**，退款只读取、不重算。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | VARCHAR(36) PK | uuid |
| `order_id` | VARCHAR(36) NOT NULL | FK payment_orders.id，索引 |
| `line_no` | INTEGER NOT NULL | 行号（1 起） |
| `item_type` | VARCHAR(32) NOT NULL | `code` / `consultation_service` / `renewal_service` |
| `item_ref` | VARCHAR(64) NULL | code=激活码值；consultation=booking_id；renewal=目标码 |
| `price_original_alloc` | INTEGER NOT NULL | 分摊前原价份额（分） |
| `coupon_alloc` | INTEGER NOT NULL DEFAULT 0 | 券分摊额（分），尾差归最后一行 |
| `amount_paid_alloc` | INTEGER NOT NULL | **分摊后实付 = price_original_alloc − 会员折后份额 − coupon_alloc**（退款上限） |
| `status` | VARCHAR(16) NOT NULL DEFAULT 'available' | `available`（未动可退）/ `used`（已激活/消耗/预约，不可退）/ `refunded`（已随退款作废） |
| `refunded_at` | DATETIME NULL | 随退款作废时间 |
| `created_at` | DATETIME | |

不变式：`Σ coupon_alloc == order.amount_discount`（优惠合计 = 会员折扣 + 券面额抵扣；单一卖家无平台/商家券拆分，尾差归最后一行保证）；`Σ amount_paid_alloc == order.amount_paid`。

分摊算法（交付时，n 行）：
1. 会员折扣先折到行：`行折后 = round(price_original × discount_pct / 100)`，尾差归最后一行；
2. 券再按行折后价比例分摊：`coupon_alloc_i = floor(coupon × row_i / Σrow)`，余数全部加到最后一行；
3. `amount_paid_alloc_i = 折后份额_i − coupon_alloc_i`（可为 0，即 0 元行，退款时无渠道金额）。

### 2.3 `payment_refunds`（新：退款申请单，全退/部分退统一）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | VARCHAR(36) PK | uuid |
| `refund_no` | VARCHAR(32) NOT NULL UNIQUE | `order_no + "R" + 3位序号`（如 `X2026…A1FR001`），即支付宝 `out_request_no` 幂等号 |
| `order_id` / `order_no` | NOT NULL / NOT NULL | 关联原订单，索引 |
| `user_id` | NOT NULL | 申请人 = 订单主人 |
| `originated` | VARCHAR(8) NOT NULL | `user` / `admin`（代录） |
| `created_by_admin` | VARCHAR(36) NULL | 代录时记录 admin user_id |
| `refund_type` | VARCHAR(8) NOT NULL | `full` / `partial` |
| `requested_amount` | INTEGER NOT NULL | 用户/代录申请额（分） |
| `approved_amount` | INTEGER NULL | admin 批准额 = 执行额（只能 ≤ 建议上限；调整须填 review_note） |
| `reason_user` | TEXT | 申请理由（用户可见全链路） |
| `reason_admin` | TEXT NULL | 审批意见 / 驳回理由 / 金额调整理由 |
| `status` | VARCHAR(16) NOT NULL | 见状态机 |
| `reviewed_by` | VARCHAR(36) NULL | 审批 admin user_id |
| `reviewed_at` / `executed_at` / `succeeded_at` | DATETIME NULL | 审批 / 渠道调用 / 渠道确认成功时间 |
| `failed_reason` | TEXT NULL | 渠道失败原因 |
| `channel_response` | TEXT NULL | 渠道回执 JSON（审计留存） |
| `line_snapshot` | TEXT NULL | JSON：批准时关联的行（line_id/code/分摊额）快照，审计用 |
| `created_at` | DATETIME | 申请时间 |

约束：
- 唯一性：`(order_id)` 上「同时最多一个 pending_review」由服务层事务校验；
- `refund_no` 唯一索引兜底幂等；
- 序号生成：事务内 `max(序号)+1`，避免并发冲突。

### 2.4 存量数据兼容（回填）

上线迁移时对存量 `granted` 订单**惰性回填**行表：首次访问（用户查可退性 / admin 审批 / 代录）时按 `meta.codes / delivered_code / booking` 生成行，分摊按当时 `amount_original/amount_discount/amount_paid` 反推（同 2.2 算法）。回填写审计日志一条（`backfilled=true`）。

## 三、状态机

### 3.1 退款单

```
pending_review ──批准──▶ refunding ──渠道成功──▶ succeeded
      │                     │
      │                     └──渠道失败──▶ failed ──重试(同refund_no)──▶ refunding
      ├──用户撤回──▶ withdrawn
      └──admin驳回──▶ rejected
```

- 「批准并执行」是一个动作：批准 → 同步调渠道 → refunding → succeeded/failed；
- failed 可无限次重试（人工兜底），**重试必须复用同一 refund_no**（支付宝幂等）；
- 渠道层唯一改造点：重试时若支付宝返回 `code=10000 且 fund_change=N`，说明该 refund_no 之前已退成功，应视为成功置 succeeded（现 `alipay.py` 会误判为失败抛异常）。

### 3.2 订单（与退款联动）

```
granted ──部分退成功──▶ partially_refunded ──累计退满──▶ refunded
granted ──全退成功──────────────────────────▶ refunded
```

退款成功时的原子动作（同一事务）：`amount_refunded += approved_amount` → 更新订单状态 → 行置 refunded → 作废码（套餐）→ 取消预约单（咨询全退）→ 全退且券未过期则退券。

## 四、业务规则（审批时重验，不信任申请时快照）

| 商品 | 全退条件 | 部分退条件 | 建议金额 |
|---|---|---|---|
| 季度/年度套餐 | 全部行 available | 选 k 个 available 行 | Σ 所选行 `amount_paid_alloc` |
| 咨询 | booking ∈ {pending_survey, submitted} | 同左，admin 手输 | 无折算，上限 = `amount_paid − amount_refunded` |
| 延期 | ❌ 不可退 | ❌ | — |
| 旧激活码 | 行 available（未 claim） | ❌ | 行实付 |
| 0 元单 | 同流程，跳过渠道调用 | — | 0 |

统一校验：`0 < approved_amount ≤ min(建议上限, amount_paid − amount_refunded)`；批准时重新读行状态，行变 used 则该行不可退、金额上限自动收缩。

## 五、API

### 用户侧
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/payment/orders/{id}/refund-options` | 可退性、行级分摊明细（码值+分摊实付+状态）、剩余可退、是否有待审申请 |
| POST | `/payment/orders/{id}/refund-requests` | 提交申请 `{refund_type, line_ids?, reason}`；full 不需要 line_ids |
| GET | `/payment/refund-requests` | 我的申请列表（含状态/驳回理由） |
| POST | `/payment/refund-requests/{id}/withdraw` | 撤回（仅本人 pending_review） |

### Admin（全部超管门控）
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/payment/refunds` | 列表（status 筛选，含订单+用户邮箱+审批留痕） |
| GET | `/admin/payment/refunds/{id}` | 详情（行快照、码去向、金额调整记录） |

## 六、幂等与并发

1. `refund_no` 唯一索引 = 渠道幂等号，同一退款重复执行在支付宝侧天然幂等；
2. 批准/重试在 DB 事务内先 `SELECT ... FOR UPDATE` 退款单（状态仍为可执行态才继续），两个 admin 同时批只有一个成功；
3. 用户提交申请：事务内校验同订单无 pending_review；
4. 批准时重验行状态与金额上限（防「申请后码被激活」竞态）；
5. 渠道超时（结果未知）：置 failed + failed_reason，重试时渠道幂等保证不多退。

## 七、明确不做（记录边界）

- 发票/红字发票模块（口径已落库，未来可回溯建发票表）；
- 支付手续费记录（渠道无回执 API，需对账单下载，暂不做，账务线下核算）；
- 自动预批/自动过期（申请长期有效，人工处理）；
- 券按比例折算返还、券过期补发。
