# Rumination v4 整改方案(tag1.6.0)

> 本文是 grill-me 会话的结论锁定文档,所有决策均经逐条确认。
> 分支:`rumination`(不影响 main 分支数据)
> 日期:2026-07-07

---

## 一、改造背景与总览

### 现状(v3)
- 7 个 step **顺序串联**,全局推进。
- step3 是"matrix 模式":3 热爱 × 5 优势 = 最多 15 个独立 combo,每个 combo 填假设或跳过。
- 每个 combo_id = `{passion_idx}{strength_idx}`(单热单优)。
- 全局 step7 = 从 N 个方向里选 1-3 个。

### 新版(v4)
- **矩阵模式成为入口**(用户一进来就是矩阵页)。
- **每个"热爱 + 优势子集"组合 = 一个独立的 combo_session**,走完整 7 步流程,产出**一张合并的结论卡**。
- 用户可在**一个热爱下选多个优势**(单选/多选均支持),并允许**为同一热爱创建多个不同子集组合**(可重复)。
- 7 步流程在右侧以**自然问答**形式驱动(用户感知不到 7 步),左侧动态展示固定组合 + 结论卡。
- 顶部 **combo tag 条**用于切换/新建/删除组合。
- 全局第 8 步:在所有已出结论卡的 combo 里选 1-3 个提交。

### 核心公式不变
**Passion x Talent x Values = True Calling**(只是流程编排重塑)。

## 二、用户交互流程

### 阶段一:矩阵页(入口)
1. 用户进入 rumination,看到矩阵选择器。
2. 勾选一个热爱 + 若干优势(可单选/多选优势,优势数量不限)。
3. **此时组合仍可调整**(改热爱、加减优势)。
4. 点"**确认创建组合**"按钮 → 进入阶段二。

### 阶段二:combo_session 视图
1. 顶部出现新的 combo tag(自增序号 `combo_1`、`combo_2`...)。
2. 左侧上半:**被选中的组合只读展示**(热爱 X + 优势 [A,B,C]),不可改。
3. 左侧下半:空(等结论卡出现)。
4. 右侧:**空白对话面板** + "**开始讨论**"按钮。
5. 点"开始讨论" → AI 开场消息出现 → 对话开始。
6. 对话中:LLM 按 mega-prompt 自主引导,通过 tool call 渐进式收集字段。
7. 字段收集充分(hypothesis 必填)→ LLM 触发结论卡生成 → 左侧下半出现可编辑结论卡。
8. 用户对结论卡执行动作(见下)。

### 顶部 combo tag 条
- 横排展示 `combo_1 | combo_2 | combo_3 | +`(可滚轮左右滑动)。
- 点击 tag = 直接切换到该 combo_session(自动保存当前草稿)。
- "+"按钮 = 回到矩阵页新建组合。
- 每个 tag 可删除(二次确认硬删除)。

### 阶段三:全局最终选择(第 8 步)
1. 用户点"**全部完成**" → 进入第 8 步视图。
2. 视图并排展示所有 `concluded` 状态的结论卡。
3. 用户勾选 1-3 个作为最终方向,提交。
4. **可返回矩阵页**(A1):新建/继续/删除组合,修改结论卡细节,第 8 步状态持久化。
5. 删除已勾选的 combo → 自动从 final_selection 移除。

## 三、数据模型(schema v4)

### 全局 rumination_state(单文件存储)
存储位置:`data/simple/reports/{report_id}/rumination_progress.json`

```python
rumination_state = {
  "schema_version": 4,
  "matrix_snapshot": {
    "passions": ["音乐", "写作", "教学"],
    "strengths": ["创造表达", "解决问题", ...],
  },
  "combo_sessions": [combo_session, ...],   # 按 created_at 排序
  "active_combo_id": "combo_3" | None,
  "final_selection": {
    "selected_combo_ids": ["combo_1", "combo_3"],
    "submitted": bool,
    "submitted_at": str | None,
  },
  "main_section": "matrix" | "combo_session" | "final_selection" | "end",
}
```

### 单个 combo_session(全部嵌入同一 JSON)
```python
combo_session = {
  "combo_id": "combo_3",                  # 自增唯一,允许相同子集重复创建
  "passion": "音乐",                       # 确认后固定不可改
  "strengths": ["创造表达", "解决问题"],     # 确认后固定不可改
  "created_at": "ISO-8601",
  "updated_at": "ISO-8601",
  "status": "discussing" | "concluded" | "abandoned",

  "messages": [...],                       # 完整对话历史(嵌入同一 JSON)
  "summary": str | None,                   # 滚动摘要,初始 None
  "summary_last_round": int,               # 摘要覆盖到的轮次

  "fields_collected": {
    "motivation": str | None,
    "hypothesis": str | dict | None,       # LLM 决定:整体一段 或 分优势条目
    "work_purposes": List[str] | None,
    "passion_mark": "忍不住想做" | "应该做" | None,
    "timing_mark": "现在" | "未来" | None,
  },

  "conclusion_card": {                     # 仅 status=concluded 时存在
    "hypothesis": str | dict,              # 必填,核心字段
    "motivation": str | None,
    "work_purposes": List[str] | None,
    "passion_mark": str | None,
    "timing_mark": str | None,
    "created_at": "ISO-8601",
    "updated_at": "ISO-8601",
  } | None,
}
```

### 关键约束
- **单文件存储**:所有 combo_sessions(含 messages)嵌入同一 JSON,便于看出 index/id 对应关系。
- **删除即彻底删除**:从 `combo_sessions` 数组移除该元素 → 整个 combo_session(含 messages)消失,**仅审计日志保留**。
- **同一时刻只 1 个 active**:`active_combo_id` 单值,切换时自动保存草稿。

### 字段集固定(5 个)
`hypothesis`(核心)+ `motivation` + `work_purposes` + `passion_mark` + `timing_mark`。

### 多优势的 hypothesis 形态(由 LLM 决定)
- **能融合** → 整体一段(str)。
- **不能融合** → 分优势条目(dict:`{strength: 假设句}`)。
- 前端/后端必须兼容两种结构。

## 四、7 步流程重塑(后端骨架,用户无感)

### 原 v3 步骤映射
| v3 步 | v3 语义(15 组合并列) | v4 处置 |
|---|---|---|
| 1 | 展示热爱+优势表 | 矩阵页入口替代 |
| 2 | 标记匹配/不匹配 | **删除**(用户勾选 = 匹配) |
| 3 | 矩阵填假设 | 合并到 combo_session 的 hypothesis 字段 |
| 4 | 加工作目的 | work_purposes 字段 |
| 5 | 激情标记 | passion_mark 字段 |
| 6 | 时机判断 | timing_mark 字段 |
| 7 | 全局选 1-3 个 | **独立为第 8 步**(全局动作) |

### v4 单个 combo_session 内部流程(后端状态机骨架)
**用户感知不到分步**,LLM 在 mega-prompt 引导下自主推进:

1. **组合确认**(motivation):"为什么选这个组合?"
2. **假设生成**(hypothesis):引导用户生成"我假设这个方向能带给我什么"。
3. **工作目的**(work_purposes):从价值观表选 1-3 个。
4. **激情感受**(passion_mark):忍不住想做 / 应该做。
5. **时机判断**(timing_mark):现在 / 未来。
6. **综合校验**:LLM 内部整合,判断是否可出卡。
7. **结论卡生成**:满足门槛(hypothesis 已填)→ 触发。

### 关键设计
- **无显式分段提示**:用户不看到"现在进入第 X 步"。
- **允许跳过**:步 1 和步 7 不可跳,其他可跳(LLM 自主判断)。
- **多优势整体被询问**:每步针对当前组合整体提问。

## 五、后端架构

### LLM 编排:轻状态机 + LLM 自主 tool call
**不使用 LangGraph 框架**(langgraph 模式仅作设计参考)。

```
用户消息 → 后端拼装(mega-prompt + 最新摘要 + 最近30轮 + tool定义)
         → LLM(原生 function calling,自主决策)
         → 后端执行 tool + 校验
         → LLM 生成最终回复
         → SSE 流式给前端
```

### Tool 定义(共 2 个主 tool)
1. **`update_field(field_name, value)`**
   - 渐进式更新单个字段。
   - **透明执行**:不展示给用户,不打断对话流。
   - 后端更新 `fields_collected`。

2. **`save_conclusion_card(fields)`**
   - 生成或更新结论卡(后端判断状态:无卡=生成,有卡=更新)。
   - **硬门槛**:hypothesis 必须已填(后端校验)。
   - **展示给用户**:SSE 推送 conclusion_card 事件。
   - 结论卡生成后对话可继续(可再次调用更新)。

### mega-prompt 设计原则
- **一大段完整**(不碎片化、不多文件拼接)。
- 内置:
  - 7 步引导逻辑(用户无感)。
  - **反问/澄清指令**(无独立 agent,无反问 tool)。
  - **结论生成信号约定**(见第七节兜底机制)。

### 后端轻状态机
- 只跟踪 `fields_collected`(字段是否已收集),**不强制顺序**。
- 状态切换 = tool call 触发的字段更新。
- 结论卡生成有硬门槛(hypothesis 必填)。

### 独立后台任务:对话摘要
- **触发**:每 30 轮(可调参)异步触发。
- **方式**:独立 summarizer prompt + 独立 LLM 调用,不污染主 mega-prompt。
- **滚动窗口**:每次摘要"上次摘要 + 最近 30 轮" → 生成新摘要替换旧摘要。
- **context 注入**:主对话 system prompt = mega-prompt + 最新摘要 + 最近 30 轮。

## 七、兜底机制(关键稳定性设计)

### 双信号约定
mega-prompt 要求 LLM 在生成结论时,**必须同时输出两个信号**:

1. **隐藏标记(只给后端)**:`<<CONCLUSION_READY>>`
   - 正则匹配,LLM 不会误触发。
   - 前端过滤,用户不可见。

2. **用户可见话术**:固定句式
   - 如:"现在我为你总结了两个假设,你可以选择其中一个"
   - 后端用关键词/模板匹配监测。

### 兜底触发逻辑(后端监测 LLM 响应)
| 信号组合 | 判定 | 动作 |
|---|---|---|
| 两个信号都有 | 正常 | SSE 推送结论卡 |
| **有用户可见话术,无 `<<CONCLUSION_READY>>`** | LLM 忘了生成 | 后端重新请求 LLM,用独立 conclusion-generation prompt + 摘要补全 → SSE 推送 |
| 有标记,无话术 | 异常 | 日志告警,补一次话术生成 |
| 都没有 | 不触发 | 正常对话 |

### 兜底执行流程(异步任务 + SSE 推送)
1. LLM 回复(含标记)流给前端(标记被前端过滤)。
2. 后端异步任务:
   - 摘要当前对话内容。
   - 用独立 conclusion-generation prompt(不污染主 mega-prompt)做内部问答。
   - 生成结论。
   - 调 `save_conclusion_card`(或直接构造)。
3. SSE 推送 conclusion_card 事件给前端。
4. 前端渲染结论卡。

### 软提醒(预留接口,初始不启用)
- **轮次兜底**:15 轮无 tool 调用 → 注入"请考虑更新字段"提示(阈值可调,初始关闭)。
- **死循环保护**:50 轮未出结论卡 → 注入"是否考虑给出结论或放弃?"(软提醒,不强制)。

## 八、用户对结论卡的操作

### 4 个动作
1. **确认**(confirm)—— 用户接受这张卡 → combo 进 `concluded`。
2. **编辑**(edit)—— 用户直接改卡内文本(走 PATCH 端点)→ 改完自动进 `concluded`。
3. **继续讨论**(continue)—— 用户不满意,回对话面板继续聊 → LLM 可能再调 `save_conclusion_card` 更新卡 → 回到等待用户操作。
4. **放弃**(abandon)—— 用户不要这个方向 → combo 进 `abandoned`,**不出卡**(若已生成则丢弃)。

### 状态约束(A1)
- **确认/放弃后**:combo 进只读,tag 灰显,**不可再聊、不可恢复**(只能删除整个 combo)。
- **结论卡永远可编辑**:即使 combo 已 confirmed,用户仍可点开卡直接编辑文本(走 PATCH 端点)。
  - 编辑卡文本**独立于 combo_session 状态**。
  - abandoned 的 combo **没有卡**(放弃 = 删卡)。

### 等待用户动作
- 结论卡生成后,**系统等待用户操作**,不自动推进。

## 十、错误处理与边界情况

| 场景 | 处理 |
|---|---|
| LLM 该调 tool 却没调(15 轮无 tool 调用) | 软提醒接口(初始不启用,阈值可调) |
| LLM 在 hypothesis 未填时调 save_conclusion_card | 后端拒绝,返回错误给 LLM,mega-prompt 要求 LLM 向用户继续追问 |
| 流式中断/网络断开 | 后端事务性写入,tool 调用成功后才落盘,整轮作废,用户重发 |
| 删除当前 active combo | active_combo_id 自动指向最近一个 combo,若无则置 null(回矩阵页) |
| 第 8 步删除已勾选的 combo | 自动从 final_selection.selected_combo_ids 移除 |
| 100 轮未出结论卡 | 50 轮软提醒"是否考虑给出结论或放弃?"(不强制) |
| 兜底:LLM 忘输出标记 | 双信号机制,有话术无标记 → 后端重新请求补全(见第七节) |

## 十三、决策汇总清单(grill 结论)

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 多选语义 | 一个热爱 + 多优势 = 一个组合单位,产出一张合并卡 |
| 2 | 组合粒度 | 一个热爱可创建多个不同优势子集组合,可重复创建 |
| 3 | combo_id | 自增序号 `combo_1`、`combo_2`...,允许相同子集并存 |
| 4 | 删除语义 | 二次确认硬删除,前台消失,审计日志保留 |
| 5 | 7 步重塑 | 步2删除,步7独立为第8步,每组合独立走流程 |
| 6 | 第 8 步 | 独立全局步骤,可回头(A1)修改组合/卡 |
| 7 | 交互模式 | 问答驱动 + 左侧动态(矩阵→结论卡) |
| 8 | 左侧布局 | 上半矩阵只读 + 下半结论卡(无 7 张小结卡) |
| 9 | 顶部 tag 条 | combo tag 横排 + 滚轮滑动 + 切换/新建/删除 |
| 10 | 编排 | 后端轻状态机 + LLM 自主 tool call |
| 11 | 字段集 | 5 个:hypothesis(核心)+ motivation + work_purposes + passion_mark + timing_mark |
| 12 | 多优势 hypothesis | LLM 决定:整体一段 或 分优势条目 |
| 13 | tool 数 | 2 个:update_field(透明)+ save_conclusion_card(展示) |
| 14 | 摘要机制 | 后台异步,30 轮触发,滚动窗口,独立 summarizer prompt |
| 15 | 反问机制 | 全内置在 mega-prompt,无独立 agent |
| 16 | 数据模型 | 单文件存储,所有 combo_session 嵌入,删除即彻底清除 |
| 17 | 迁移 | 不迁移,预留脚本,一刀切 v4 |
| 18 | API | /rumination-v4/ 前缀,9 个端点,SSE 流式 |
| 19 | 前端路由 | 复用现有,内部重写,两阶段动作(A2) |
| 20 | 状态管理 | Zustand + 后端单一数据源,懒加载+缓存 |
| 21 | 错误处理 | 事务性写入,自动收敛,软提醒(预留) |
| 22 | 兜底机制 | 双信号(隐藏标记 + 用户可见话术),异步任务+SSE,独立 prompt |
| 23 | 用户操作 | 4 个动作(确认/编辑/继续讨论/放弃),结论卡永远可编辑 |
| 24 | abandoned | 无卡(放弃 = 删卡) |
| 25 | 部署 | 装 zustand,分支改造不影响 main |
