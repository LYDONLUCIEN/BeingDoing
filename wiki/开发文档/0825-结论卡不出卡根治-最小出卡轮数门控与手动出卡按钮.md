## 一、现状机制（本次改完后的口径）

### 1. 状态机（四阶段 values/strengths/interests/purpose；rumination 不走此协议）

```
none（未出过卡）
  │  路径 A：主模型在回复末尾自觉输出 [STATE_JSON]{"state":"pending_ready","draft":{...}}
  │  路径 M：满 11 轮未出卡时，用户点「对话结束无法进行下一步?点击这里」按钮
  │         → POST /simple-chat/conclusion/request 直接生成草案
  ▼
pending（草案卡已弹出，输入框锁定，必须点按钮）
  ├─ 点「确认没有问题」→ POST /thread/complete → confirmed + thread_completed（阶段完成）
  └─ 点「我想再聊聊」→ POST /thread/reopen → rejected（卡折叠、输入解锁、记 feedback）
       └─ 之后模型自觉再出卡；满 3 轮用户消息未出 → 后端 retrigger 强制生成兜底
confirmed → 等用户点卡片「确认」→ thread_completed
```

关键事实：

- **pending ⇒ 卡已推出**：置 pending 与推 `dimension_conclusion` SSE 事件在同一段代码里成对发生；断流也有刷新时前端从 meta 补卡（hydrate 兜底）。瓶颈从来只在 `none → pending`。
- **出卡后输入框锁定**（`pendingConclusionChoiceBlocksChat`，2026-04-11 起）：用户只能用按钮表态，不能打字回复卡片。因此 pending 判定器（`_decide_pending_action_by_llm`）自 4-11 起近乎死代码，仅剩流式竞态可达。
- 后端在 `none` 期间对对话零结构化记录（不逐轮提取 keywords/摘要），keywords 只存在于草案/正式卡内。

### 2. 最小出卡轮数门控（本次新增）

- 常量 `CONCLUSION_MIN_USER_TURNS = 11`（`simple_chat_routes.py`）。
- 四阶段所有用户**前 10 轮不出卡**：`state=none` 且用户消息数（含当前条，消息先落盘再计数）< 11 时：
  - 模型输出 `pending_ready` → 拦截不置 pending，记日志 `[state_json] pending_ready suppressed by min-turns gate`；
  - 注入段 `build_conclusion_state_injection(gate_active=True)` 改口径：「深入探索期，即使对方已明确认可也不要输出 STATE_JSON；不要呈现『最终总结/请确认』式收口话术，继续深入探索」——避免 AI 嘴上总结了但卡没出来的割裂；
  - rejected 后 retrigger 兜底同样被门控拦住。
- **只拦首次出卡**：`state=rejected`（出过卡被否定，含存量数据）的重新出卡不受限。
- admin 调试工作区（`_can_bypass_flow_limits`）不受限。
- 产品效果：试用码用户 values 限 10 轮 → 永远出不了卡，必须升级完整版才能进入出卡与后续阶段，转化路径天然成立。

### 3. 手动出卡按钮（本次新增）

- **显示条件**（前端 chat 页）：非 rumination、阶段未完成、报告未解锁、**从未出过卡**（消息流无 dimension_conclusion）、用户消息 ≥ 11 条。
- **位置与动画**：输入框上方胶囊按钮；首次出现 spring「冒泡长出」（opacity+y+scale）；闲置提醒——出现 10s 后抖动一次、继续闲置满 60s 再抖一次，**每阶段封顶 2 次**，页面不在前台/正在输入/流式中/引导任务中不打扰。
- **点击语义**：直接生成草案卡（**不做"先判定聊完没"的守门**）——草案卡自带「确认/再聊聊」，出早了用户点"再聊聊"即可自我纠错，无死路。后端 `POST /simple-chat/conclusion/request` 走 `check_dimension_complete(skip_completion_check=True)`，与 rejected retrigger 同一条生产链路；已有 pending/confirmed 幂等返回；<11 轮 400；生成失败 503。
- **失败不静默**：按钮原地变红「生成失败，点击重试」。
- 文案：zh「对话结束无法进行下一步?点击这里」/ loading「正在生成阶段小结…」。

### 4. STATE_JSON 可观测性（本次新增日志，此前全部静默）

| 日志 | 位置 | 场景 |
|---|---|---|
| `[state_json] unclosed block ...` | `stream_utils.split_visible_reply_and_state` | 块未闭合（典型：8192 截断） |
| `[state_json] parse failed ...` | 同上 | 块完整但 JSON 非法 |
| `[state_json] pending_ready without valid draft ...` | 主链路 path A | draft 缺失/非对象 |
| `[state_json] pending_ready suppressed by min-turns gate ...` | 主链路 path A | 门控拦截 |
| `[conclusion_gen] pending_ready refine timeout/failed ...` | 主链路 path A | 25s refine 失败（回退原始 draft） |
| `[conclusion_request] timeout/failed ...` | 手动端点 | 按钮生成失败 |

## 三、本次排查的关键发现（为什么以前总"差点修好"）

1. **首次出卡零兜底是设计性后果**：4 月收敛下线的不是"判定器不好用"，而是"双产品入口"；judge gate 是陪葬品。此后 `none→pending` 100% 靠模型自觉，而提示词要求「用户明确点头确认才输出」→ 模型保守 → 用户不引导就不出卡。
2. **pending 判定器早已近乎死代码**：3-26 它为"打字回复卡片"的 UI 而生；4-11 输入锁上线后用户不能打字表态，判定器仅剩竞态可达。4-22 的「continue 并入 rejected 毁卡」防的是"卡片悬挂"，而悬挂 11 天前已被输入锁解决——**过期补丁**。
3. 因此本次**不做**：K=3 continue 保留方案、判定器加上下文（shown_at 窗口）、守望者自动判定（满 N 轮后台盯"漏判确认"）——均被否决，理由分别是死路径、死路径、会打断对话+成本翻倍。

## 四、本次确定的决策（grill 定稿）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | 兜底形态 | 手动按钮，非自动守望者 | 守望者在用户继续聊时出卡会打断/引导偏；挂判定每轮烧 token、尾部延迟；按钮零打扰零常态成本 |
| 2 | 点击语义 | 直接出卡，不先跑完成判定 | 草案卡可拒绝（再聊聊），自我纠错无死路；判定器是多余守门员 |
| 3 | N 值 | 11（不是 6/8/10） | 试用码 values 限 10 轮，N=11 ⇒ 试用期不出卡，升级后才出 |
| 4 | 10 轮内模型自觉出卡 | 也拦截 | 用户明确要求"出卡了也要拦截不出，升级正式版以后才出" |
| 5 | 适用范围 | 四阶段所有用户 | 门控与按钮均为四阶段通用 |
| 6 | 门控粒度 | 仅拦首次出卡（state=none） | rejected 线程（出过卡）重新出卡不受限；回归测试 `test_flow_6`/savepoint 用例倒逼出此修正 |
| 7 | 按钮文案 | 「对话结束无法进行下一步?点击这里」 | 产品指定 |
| 8 | 提醒动画 | 冒泡长出 + 闲置抖动（10s/60s 各一次，封顶 2 次） | 告知"多了个东西"，不催促；闲置检测是前端职责（后端不知道用户正在打字） |
| 9 | 失败处理 | 503 + 按钮变红「生成失败，点击重试」 | 不静默 |
| 10 | max_tokens | 不动，维持固定 8192 + 截断日志 | 不存在"不限制"（不传=服务端默认 4096）；逐级放宽仅 balance judge（8000/16000），其余平铺 8192 |
