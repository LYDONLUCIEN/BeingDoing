# 优惠券多次核销 + 激活码/优惠券码格式区分 — 设计定稿

> 2026-10-06 grill-me 拷问定稿（三轮、10 项决策）。
> 关联：`订单系统退款设计.md`（退款系统 2026-10-05 已上线，本设计的退款联动以其为准）。

## 背景

1. 优惠券目前严格单次核销（`unused→locked→used` 单槽字段），运营需要"一张码转发 n 人、共核销 n 次"的促销码能力。
2. 激活码（10 位裸码）与优惠券码（12 位裸码）同字符集、同形态，用户无法区分，客服口述/手输混淆严重。

## 定稿决策（10 项）

| # | 决策 | 结论 |
|---|------|------|
| D1 | n 的语义 | **总核销 n 次，不限人**（促销码模式）；n=1 完全等价现状 |
| D2 | 核销记录存储 | **新表 `coupon_redemptions`**（每次锁定/核销一行，退款按行回退）；不回填历史 |
| D3 | 码格式 | 优惠券 `Q-` + 8 位；激活码 `OPENLIFE-XXXX-XXXX-XXXX`（12 位 body，3 组×4）；字符集剔除 `0/O/1/I/L` |
| D4 | n>1 券归属 | **一律流通券**：不可绑 owner，邮件券池（draw_from_pool）跳过 n>1 |
| D5 | 同人重复核销 | **每用户每券限 1 次**（n>1 时；n=1 本来就一次） |
| D6 | 中途停用 | **新增停用/启用开关**：已核销名额保持有效，剩余名额立即冻结；与作废（void）分开 |
| D7 | n 上限 | **≤ 10000**；admin 表单实时展示「面额 × n = 总补贴负债」 |
| D8 | 输码容错 | **归一（大写/去空格换行/全角横杠→`-`）+ 漏前缀自动补全 + 轻量内存限流**，全套 |
| D9 | validate 响应 | **不展示剩余名额**；抢完/每人一次用完时报错文案提示 |
| D10 | 存量兼容 | 存量裸码（10/12 位无连字符）**精确匹配永久可用**；新码含 `-` 前缀，与存量永不碰撞 |

### 拷问中推翻/澄清的假设

- "用户都复制粘贴不会输错" — **不成立**：长码在邮件/微信必然折行（复制截断）、富文本复制会把 `-` 变全角 `－` 或空格、地推/口述场景真实存在（选择防混淆字符集即已默认手输存在）。故归一化是止血项不是优化项。
- 激活码 body 若为 16 位，`裸 12 位→OPENLIFE-` 自动补全会与**存量 12 位裸券码**在同一输入框冲突 → 定为 12 位 body，且**补全规则按输入上下文（券码框/激活码框）分别定义**，见歧义矩阵。

## 一、数据模型

### 1.1 `coupons` 表加列（alembic 024）

```python
max_uses     = Column(Integer, nullable=False, default=1)   # 总核销次数上限（D1/D7）
used_count   = Column(Integer, nullable=False, default=0)   # 已核销次数（原子自增）
locked_count = Column(Integer, nullable=False, default=0)   # 锁定中次数（原子自增/自减）
suspended_at = Column(DateTime, nullable=True)              # 停用时间（D6；NULL=未停用）
```

- 存量券迁移时 `max_uses=1, used_count=0, locked_count=0`，`locked/used` 状态行 `used_count=1 / locked_count=1` 对齐（供守卫与列表展示，**不**改动单槽字段）。
- 单槽字段（`used_by_user_id/used_order_id/used_at/locked_order_id`）**保留不动**：n=1 券继续双写，admin 列表/我的券查询对 n=1 完全沿用旧路径。

### 1.2 新表 `coupon_redemptions`（D2）

```python
class CouponRedemption(Base):
    __tablename__ = "coupon_redemptions"
    id         = String(36) PK
    coupon_id  = String(36) FK coupons.id, index
    order_id   = String(36) FK payment_orders.id, unique   # 一单一券一核销行
    user_id    = String(36), index
    status     = String(16)   # locked / used / released / refunded
    locked_at  = DateTime
    used_at    = DateTime
    refunded_at = DateTime
```

- 只记**新发生**的锁定/核销（含 n=1 新券），历史已核销数据不回填（展示沿用单槽字段）。
- 退款全额成功 → 该订单对应行 `used → refunded` + `used_count -= 1`。

## 二、状态机与并发

### 2.1 n=1（现状原样保留）

`unused → locked → used`；`void` / 派生 `expired`。锁券仍用 `UPDATE ... WHERE status='unused'` 影响行数守卫，**额外**同步维护 `locked_count/used_count` 并插 redemptions 行（双写，旧查询零改动）。

### 2.2 n>1（新语义）

- 券级 `status` 恒为 `unused` 直到 `used_count >= max_uses`；派生态：
  - `used`：`used_count >= max_uses`（名额耗尽）
  - `suspended`：`suspended_at` 非空（D6，优先级高于 used 展示可并列）
  - `expired`：unused 且 `expires_at` 已过（名额随过期整体作废）
- 锁定不再改券级状态，改占名额：`locked_count`。

### 2.3 锁券原子守卫（核心）

```sql
UPDATE coupons SET locked_count = locked_count + 1
WHERE id = :id
  AND status = 'unused'
  AND suspended_at IS NULL
  AND used_count + locked_count < max_uses      -- 名额守卫（D1）
  AND (expires_at IS NULL OR expires_at > now)
  AND NOT EXISTS (                              -- 每用户限 1 次（D5，仅 n>1 需要子查询）
        SELECT 1 FROM coupon_redemptions r
        WHERE r.coupon_id = :id AND r.user_id = :uid
          AND r.status IN ('locked','used'))
```

影响行数=1 → 同事务插 redemptions 行（status=locked）→ commit。rowcount=0 → 按不存在/停用/已抢完/每人一次/过期分别回查给出准确错误文案。SQLite/PG 行为一致（无需 FOR UPDATE）。

### 2.4 各流转对 counters 的维护

| 动作 | redemptions 行 | counters |
|---|---|---|
| 下单锁定 | insert `locked` | `locked_count+1` |
| 关单释放 | `locked→released` | `locked_count-1` |
| 支付核销 | `locked→used` | `locked_count-1, used_count+1`；n=1 时同步写单槽字段（双写） |
| 全额退款退券 | `used→refunded` | `used_count-1`；n=1 时同步回退单槽字段（现状行为） |
| 停用/启用 | 不动 | 只改 `suspended_at` |

`CouponService.return_coupon_on_refund(coupon_id)` 签名改为 `(coupon_id, order_id)`（按行回退）；refund_service 调用点同步（仍仅 `fully_refunded` 时触发，口径不变）。

### 2.5 券池与归属（D4）

- `create_coupons(..., max_uses)`：n>1 时强制 `owner_user_id=None`，否则 ValueError。
- `draw_from_pool` 查询加 `max_uses = 1` 过滤。

## 三、码格式（D3/D10）

### 3.1 生成

| | 新格式 | 例 | 字符集 |
|---|---|---|---|
| 优惠券 | `Q-` + 8 位 | `Q-K3M7X9A2` | 大写字母+数字剔除 `0 O 1 I L` |
| 激活码 | `OPENLIFE-` + 12 位 body 分 3 组 | `OPENLIFE-9F2K-8M4P-7X1D` | 同上 |

- 全部 `secrets.choice`（激活码现状 `random.choices` 顺手升级，激活码是付费商品凭据）。
- 生成点各仅一处：`CouponService._generate_code`、`SimpleActivationManager.create_activation`（trial/full 统一新格式）。
- 长度核对：`Q-`8位=10 字符（coupons.code String(32) ✓）；激活码 23 字符（JSON 文件存储无约束；abuse/analytics 的 String(64) 引用列 ✓；需核 `PaymentOrder.delivered_code` 长度，23 < 32 ✓）。
- 存量裸码无 `-`，新码必有 `-` → **码空间永不相交**，精确匹配即兼容。

### 3.2 归一化与自动补全（D8）— 新 util `app/utils/code_format.py`

```
normalize_user_code(raw, context) -> str
  1. trim；全角横杠 － — – _ → -；去所有空白（含换行，治折行截断）；转大写
  2. 自动补前缀（严格长度触发，context 分流）：
     - context=coupon：无 - 且长度 8 → Q-前缀
     - context=activation：无 - 且长度 12 → OPENLIFE-前缀
     - 长度 10/12 裸码在各自 context 中不触发补全 → 存量码原样匹配
```

**歧义矩阵**（裸 12 位在两个 context 撞型，靠 context 分流兜底）：

| 输入 | 券码框 | 激活码框 |
|---|---|---|
| 裸 12 位（存量券） | ✅ 原样匹配 | ❌ 补成 OPENLIFE-xx → "激活码不存在"（输错框，报错可接受） |
| 裸 12 位（新激活码 body） | ❌ "券码不存在"（输错框） | ✅ 补 OPENLIFE- |
| 裸 10 位（存量激活码） | ❌ 券码不存在 | ✅ 原样匹配 |
| 裸 8 位（新券 body） | ✅ 补 Q- | ❌ 激活码不存在 |

### 3.3 限流（D8）— 新 util `app/utils/rate_limit.py`

- 轻量内存滑动窗口（单进程 uvicorn 够用；局限写进 docstring）。
- `POST /payment/coupons/validate`、`POST /simple-auth/activate`：默认 **10 次/分钟/IP**，超限 429。

## 四、API 变更

### 用户侧
- `POST /payment/coupons/validate`：响应不变（**不加** remaining，D9）；n>1 券的错误文案：「该券已被抢完 / 该券每个账号限用一次」。加限流。
- `GET /payment/my-coupons`：`used` 组增加 n>1 券条目（来源 redemptions where user_id=me：code/amount/used_at/used_order_no）；`available` 组不变（n>1 不归属，不出现）。
- `POST /simple-auth/activate`：输入归一化 + 限流；响应结构不变。

### Admin 侧（admin_payment.py）
- `POST /admin/coupons`：请求体 + `max_uses`（1-10000，默认 1）；n>1 且带 owner → 400。
- `POST /admin/coupons/{id}/suspend` / `resume`（新）：suspended 态可恢复；used/void 不可停用（无意义）。
- `GET /admin/coupons`：序列化 + `max_uses/used_count/locked_count/suspended_at`；n>1 派生态按 2.2；`DELETE 作废` 规则不变（仅 unused 且 used_count=0）。

## 五、前端变更

- **admin/payment coupons tab**：创建表单 +「可用次数」字段（默认 1），实时显示 `面额 ¥x × n = 总补贴 ¥y`；列表加「已用/总量」列 + 停用/启用按钮 + 停用徽标；页首说明文案补多次券语义。
- **PurchaseModal（券码输入）**：输入框 `normalize_user_code(ctx=coupon)`（前端同款归一：大写/去空白/全角横杠/裸 8 位补 Q-），placeholder 改为新格式示例。
- **dashboard/codes 激活码绑定框**：同上 ctx=activation，placeholder 更新。
- **CouponsSection（我的折扣券）**：used 组展示多核销记录（后端已给数据，前端透传即可）。

## 七、测试清单（关键用例）

1. n=1 新券走全链路 → 行为与现状逐字段一致（回归底线）
2. n=3 券：3 个不同用户依次锁→核销；第 4 人 validate/lock 报「已被抢完」
3. 同一用户第二次锁 n>1 券 → 「每个账号限用一次」（validate 与 lock 双端）
4. 并发：n=2 券 5 个并发锁 → 恰好 2 成功（SQLite 串行 + PG 均验证）
5. 关单释放：名额回补（locked_count-1），释放后可再锁
6. 全额退款：redemption 行 refunded、used_count-1、n>1 券恢复可用；n=1 券回退单槽字段（现状）
7. 停用：锁新单被拒、已核销不受影响、启用后恢复；作废仍要求 used_count=0
8. 码格式：生成均含前缀且字符集合法；归一化矩阵（全角横杠/折行空格/裸 body 补全/跨框输错）
9. 存量裸码（10/12 位）validate/activate 原样可用
10. 限流：第 11 次/分钟 → 429；不同 IP 互不影响
