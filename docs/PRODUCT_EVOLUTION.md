# 新产品边界与实施顺序

## 已确认方向（2026-10-12，项目所有者）

所有产品共用现有账户体系；订单、优惠券和历史激活码信息可关联查询。新产品主要提供月/年订阅，也可能出售一次性课程、数据和知识内容，未来可能使用购物车。新产品不必发行激活码或生成报告，但可经激活码索引访问历史报告。

[ADR-0024](adr/0024-shared-account-product-boundaries.md) 记录这个决定。此文是后续实现边界，不把未来能力写成已上线功能。本次不改变真实价格、不创建订阅扣款、不迁移服务器数据。

## 明确分开四件事

| 概念 | 共享/独立边界 | 本次代码现状 |
| --- | --- | --- |
| 账户身份 | 共用 users.id 与现有认证/恢复流程 | 已存在，保持 |
| 交易 | 订单、金额分摊、券核销、退款审计可复用 | 当前单商品订单，不是真正多商品购物车 |
| 订阅与权益 | 按产品、能力、期限判定；付款触发交付，但付款状态不是全部权限 | 只有未上线的老会员预留模型，不能直接上线为新月/年产品 |
| 探索与报告 | 现有激活码关联探索；报告访问独立鉴权 | 已存在，可作为新产品调用的只读能力 |

## 接口/字段设计原则

- 新产品引用 users.id；邮箱/手机号/昵称只作属性。禁止复制一套按邮箱拼接的账户表。
- 产品目录区分 product、sku、计费方式和交付类型；月/年是计费周期，产品权限另有 entitlement 定义。老 lifetime 按原含义保留。
- 现有 quarterly_package/annual_package 是一次性探索套餐，名字中的 annual 不能作为年订阅判断依据；vip_level 继续只是旧模型档位。
- 购物车结算需明确多 SKU 明细与数量、分摊、券适用范围、部分退款和幂等交付。现有 payment_order_lines 围绕同一套餐交付码拆行，不能仅放开 quantity 就声称支持购物车。
- 激活码是历史资源查询入口，不是跨产品访问凭证。服务端解析 report_id 后验证请求账户是激活人，或是获授权购买者，并应用完成度/审核规则；普通订阅不自动开放其他人的报告/对话。
- 新权益缓存必须可由权威交易/订阅状态重建；保留来源 order_id/subscription_id/product_id 等追溯关系。字段名与状态待设计定稿，不在此先创建空表。

## 开发前仍需产品决定

| 决策 | 影响 |
| --- | --- |
| 自动续费扣款还是到期手动续费；试用/宽限/取消何时生效 | 渠道签约、订阅状态机、Webhook 幂等与撤权时间 |
| 月/年套餐具体包含什么能力，能否跨产品通用 | 产品目录、权益及授权范围 |
| 升降级、补差、退款、暂停和赠送政策 | 周期计算、账务与权益回滚 |
| 券可用于首期/续期/一次性商品中的哪些，是否允许混合结算 | 券范围和分摊规则，不能默认老券全产品通用 |
| 历史报告仅本人可读还是包含已授权购买者；产品展示形式 | 报告访问服务契约（不能削弱既有隐私边界） |

## 可执行的下一阶段

1. 固定订阅状态和权益矩阵，用账单/周期边界/取消/退款场景定契约。
2. 以共享账户为前提增加产品目录和权益查询服务；先单产品订阅闭环，再扩展购物车，避免同时改多个账务变量。
3. 隔离测试库实现迁移与交付幂等，复用现有订单/券/退款回归；服务端验证回调签名与金额。
4. 加入历史报告只读查询，覆盖本人、获授权购买者、未授权账户和未审核报告。
5. 经完整测试环境演练后部署；旧探索和历史会员字段保留解释及迁移记录。
