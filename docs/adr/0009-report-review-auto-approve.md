# ADR-0009: 报告阻塞式审核 + 随机时限自动批复

**状态**: accepted
**日期**: 2026-07-20
**决策者**: 产品 + 开发 Grill

## 背景

季度/年度套餐承诺「报告由人工校验与逻辑纠偏，确认后交付」，但现有报告是 LLM 直出、即时可见，没有任何审核环节。真正的人工阻塞审核意味着用户要等不确定时长。

## 决策

报告生成后进入 `pending_review`（用户侧显示「审核中」），admin 确认后才可见。兜底：生成时随机确定 3~24 小时的审核时限，超时未处理则**自动批复通过**——后台如实记录 `auto` 批复类型，但**用户侧只感知「管理员审核通过」**，不暴露自动事实。

## 后果

- 这是刻意的「善意伪装」：用户通知文案统一为管理员审核结果。未来读者不要当成 bug 修复掉用户侧文案。
- 需要：报告审核状态字段与随机截止时间、APScheduler 周期自动批复任务、admin 审核列表（人工确认/查看自动批复记录）、交付通知邮件。
- 审核时限随机（非固定值）是为了避免用户摸索出固定等待规律。

## 修订（2026-07-27）：审核计时锚点后移 + 审核期间预生成

**问题**：原实现把 `pending_review` + 随机 3~24h 时限写在**报告记录创建时**（激活码激活/首次会话 `ensure_report`）。用户走完五阶段通常远超 24h，等用户到报告页时调度器早已自动批复——审核环节形同虚设（用户从未见过「审核中」）。

**修订决策**：

1. 新增 `review_status = not_started` 状态：新建报告记录只标记 `not_started`（不计时、无 deadline）。存量无字段记录维持祖父豁免视为 `approved`，不受影响。
2. 计时起点改为**用户进入报告页**（`GET /export/my-report-id`，报告 view 页首调）且**五阶段均已完成**（`_report_portal_unlocked` 判定）的那一刻：`not_started → pending_review` + 随机 3~24h 时限。直连 PDF 端点（`trigger/status/download`）走 `_review_block_payload` 兜底同样的转移逻辑；五阶段未完成时一律阻塞并返回 `not_started`。
3. **审核期间报告已在自动生成**：转 `pending_review` 的同一时刻后台异步预生成报告 markdown（`_kick_pdf_generation`，复用既有缓存机制），批复通过后下载秒出；预生成失败则由下载路径重试兜底。
4. 前端报告页新增 `not_started` 占位（「报告尚未解锁」）；admin 审核列表新增「未开始」badge 与筛选项。

「善意伪装」语义不变：自动批复的用户侧文案仍与人工一致。
