# ADR-0013: 统计看板——事件时间口径漏斗 + 埋点业务同库（SQLite），不建 Cohort、不提前上 PG

**状态**: accepted
**日期**: 2026-08-05
**决策者**: 产品 + 开发 Grill（grill-with-docs）

## 背景

admin「埋点与 Token 统计」页（`/admin/analytics`）要扩展为漏斗级统计看板：浏览(PV) → 注册 → 试用开聊 → 完成10轮 → 付费 → 得到报告，外加日活、激活码计数、实收与理论收益，支持按日/月/自定义时段查询。现状三个缺口：

1. **PV 与登录日活采集完全缺失**：前端无页面埋点、后端无访问日志中间件、nginx 未开 access_log；`users.last_login_at` 只存最后一次登录，无历史序列；
2. **所有统计端点无时段筛选参数**，全量聚合；
3. **漏斗数据横跨两种存储**：注册/订单/对话轮次埋点在 SQLite（`users`/`payment_orders`/`analytics_chat_turns`），试用码使用、激活码总数、报告审核通过时间在 JSON（`activations.json`/`record.json`）。

## 决策

- **漏斗采用事件时间口径**：每个环节独立计数「该环节事件发生在选定时段内的人/次数」，**不做注册队列（Cohort）回溯**。环节定义见 CONTEXT.md「统计看板」节（试用开聊 = 发出 ≥1 条 values 消息；完成10轮 = 第 10 条 values 消息时间；付费 = paid/granted 未退款订单去重用户按 paid_at；得到报告 = 审核通过时间含自动批复）。
- **存储维持 SQLite，埋点与业务同库**：新增通用事件表（页面浏览、登录/刷新活跃）落现有 `app.db`，**不引入第二个存储、不因此提前触发 PostgreSQL**。本决策是 ADR-0011 阶段 2「条件触发」的延续确认——统计看板的聚合查询量级（COUNT/SUM + 时间分组）不构成切换扳机。
- **统计服务跨 DB + JSON 聚合**：JSON 侧数据（激活码、报告审核）由统计服务读 `SimpleActivationManager`/`ReportRegistry` 实时聚合，与 DB 侧结果合并；**不为此提前启动 ADR-0011 阶段 1（JSON 全量入库）**。
- **PV/日活无历史回填**：两指标自埋点上线之日起统计，历史时段显示无数据；其余环节（注册/10轮/付费/报告/收益）均可回溯历史。

## 理由（拒绝的备选）

- **Cohort 口径**（按注册时段圈人、追踪最终转化）：能回答"这批新用户转化质量"，但数字随时间回填变化、口径解释成本高，且与"看板看趋势"的主诉求不符；如未来需要可作二期视图叠加，不影响事件时间口径的埋点结构。
- **nginx access_log 统计 PV**：SPA 路由切换不产生请求，只能统计到首页加载；UV 靠 IP 不准；引入日志解析管道。前端埋点（sendBeacon + visitor_id cookie）零依赖登录、可按页面细分。
- **提前上 PG / 引入 ClickHouse 等分析库**：当前主库 1.2MB 量级，聚合查询毫秒级；提前承担第二套存储的运维与跨库拼接成本，正是 ADR-0011 明确否决的"DB+JSON 拼接之痛"的重演。
- **为统计提前做 JSON 入库（ADR-0011 阶段 1）**：阶段 1 是 schema 重设计级工程，与看板需求耦合会双重延期；统计层读两边是已被 admin dashboard overview 验证过的过渡做法。

## 后果

- 新增事件表与统计端点均带 `created_at` + 时段参数，后续若启 Cohort 视图可直接复用。
- 通用事件表只接 PV 与活跃两类事件；未来其他埋点（按钮点击等）可复用同表结构。
- 「纯利润」在看板中的展示名为产品口径，实为**实收**（Σ amount_paid，剔除退款单），不含成本；CONTEXT.md 已记为「实收（纯利润）」。
- 若 ADR-0011 阶段 1 日后启动，统计服务的 JSON 侧聚合逻辑需随激活码/报告入库改为纯 SQL，属预期内重构。
