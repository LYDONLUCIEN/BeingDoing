# ADR-0017: 报告后处理修正管线 —— 一次生成 + 按章节分步修正

**状态**: accepted
**日期**: 2026-08-12
**决策者**: 产品 + 开发 Grill

## 背景

报告（LLM 一次性生成 markdown → HTML → WeasyPrint PDF）暴露出一批"单点质量问题"：表格无框线、标题层级错乱（h4/h5 无样式）、列表符 `-`/`*` 混用且部分行未被解析成列表、分页符偶发不生效、「给读者的一封信」字数/分页不稳定（目标 800 字左右且信+签名一页内）。

这些问题的共同特征是：**主提示词一次性生成的产出天然不稳定**，而靠继续往主提示词里加约束（字数、格式、分页）遵从度有限且互相干扰。

## 决策

保持**主提示词一次性生成不变**，在 markdown 生成之后、渲染 PDF 之前新增**报告后处理修正管线（Report Post-Processing）**：

- **按章节切分**：将报告 markdown 解析为 section 列表（扉页 / 第一章~第八章 / 信件等）。
- **两类处理器，可插拔、分步扩展**：
  1. **确定性规则**（无 LLM，先行执行）：行首 `* ` 列表符统一为 `- `；分页标记规范化（提示词侧改为输出独立短标记 `<<<PAGEBREAK>>>`，后处理统一替换为 `<div class="pb"></div>`，不再依赖 LLM 输出合法 HTML/内联样式）。
  2. **LLM 修正器**（针对特定章节的特定问题，各自独立 prompt）：首个为**信件压缩器**——检测「给读者的一封信」超过约 900 字时，用专用 prompt 重写至 750-850 字，配合信前强制分页与 CSS 字号/行距约束，保证信+签名稳定在一页内。
- **兜底原则**：任一修正器校验失败或调用失败，保留原文，不阻塞报告产出。

## 备选方案

- **两步生成法**（主报告 + 信件独立生成调用）：对信件可控性相当，但每个新章节问题都要改主生成流程，无法形成统一的"逐章节修正"框架——被否。
- **只强化主提示词约束**：零额外成本，但 LLM 对字数/分页等硬约束遵从度不稳定，历史上已验证不可靠——被否。

## 后果

- 报告生成增加一次（有条件的）LLM 调用：仅当信件超长约 900 字时触发压缩，正常情况零额外成本。
- 后续每个章节级质量问题（如某章结构缺失、表格格式修复）都以新增处理器的方式扩展，主提示词保持稳定。
- 分页符契约变化：`report_system.yaml` 中分页指令从 `<div STYLE="page-break-after: always;"></div>` 改为 `<<<PAGEBREAK>>>` 标记，渲染端只认后处理产出的 `<div class="pb">`（CSS `.pb { page-break-after: always; }`）。
- 术语已入 CONTEXT.md：「报告后处理修正 (Report Post-Processing)」。
